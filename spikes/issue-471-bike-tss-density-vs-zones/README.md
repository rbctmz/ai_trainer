# Spike: плановый TSS вело vs зоны шагов воркаута

- Issue: #471
- Дата проверки: 2026-08-18
- Владелец: DeepSeek-агент (по запросу атлета)
- Бюджет: локальная SQLite, без сети и внешних вызовов; ~1 ч

## Вопрос

Совпадает ли плановый TSS лёгких вело-сессий с нагрузкой, которую дают
целевые зоны мощности самого воркаута при исполнении по серединам зон?

## Гипотеза

Зоны шагов билдеров каталога (endurance/recovery/progression) дают
плотность ~40 / ~22 / ~45 TSS/ч, а материализатор выбирает длительность и
хранит плотность по `_TARGET_DENSITY` (55 / 35 / 70). Поэтому план
систематически завышает TSS лёгких вело на ~25-45%, а фактический TSS
(power_tss_bike) при точном исполнении зон оказывается ниже плана — атлет
выглядит «недорабатывающим», хотя исполняет предписание верно.

## Что опровергнет гипотезу

Совпадение stored и zone-implied плотности в пределах ±10% по всем
steady-state сессиям активного плана, либо фактический TSS станок-сессий,
далёкий от zone-implied значения.

## Границы и риски

Проверяются только материализованные вело-сессии активного checkpoint #119 и
две фактические станок-сессии 17-18.08. Интервальные шаблоны (tempo/threshold/
vo2/neuromuscular/race_pace) исключены из строгого вердикта: оценка по
серединам зон занижает их истинный TSS (нужно NP-моделирование) — для них
приводится только справочное наблюдение. Эксперимент read-only, внешних
записей не делает.

## Данные и фикстуры

Локальная `ai_trainer.db` (не коммитится): checkpoint #119, сессии с
`materialized_steps` и `parameter_snapshot`; фактические активности
24013043328 / 24026706443 (`power_tss_bike`, `tss_ftp_used=172` из
athlete_profile/Intervals.icu). Персональные метрики в репозиторий не
попадают — в спайке только агрегированные плотности и дельты.

## Окружение и версии

Python 3.11 (venv `ai_trainer_env`), каталог `workout_catalog_v3`,
материализатор `workout_materializer_v2`, локальный SQLite.

## Подход

`evidence.py` считает zone-implied TSS: для каждого шага берётся середина
зоны мощности [low, high], TSS = Σ часы × 100 × (середина/FTP)², плотность =
TSS × 60 / длительность. Сравнивается с хранимыми `total_tss`/`tss_per_hour`
сессии. Скрипт не импортируется продуктом и не модифицирует данные.

## Запуск

Из корня репозитория:

    ai_trainer_env/bin/python spikes/issue-471-bike-tss-density-vs-zones/evidence.py

Побочные эффекты: нет (read-only).

## Наблюдение

Ground truth (станок, power_tss_bike):

| Дата | Факт | zone-implied | Δ факт |
|------|------|--------------|--------|
| 17.08 | 28.6 TSS (NP 113) | 26.7 | +7% |
| 18.08 | 28.2 TSS (NP 112) | 26.7 | +6% |

Факт совпадает с зонами; план — нет. Средняя плотность по steady-state
шаблонам активного плана:

| Шаблон | stored TSS/ч | zone-implied TSS/ч | Δ | n |
|--------|--------------|--------------------|-----|---|
| bike_aerobic_endurance | 50.9 | 40.0 | +27% | 8 |
| bike_aerobic_progression | 64.4 | 44.9 | +43% | 4 |
| bike_recovery_spin | 32.1 | 22.4 | +43% | 3 |

Примеры 40-минутных сессий: 17.08 план 32.9 vs зоны 26.7 (+23%); 18.08 план
36.5 vs зоны 26.7 (+37%). Причина: `_TARGET_DENSITY` (endurance=55,
progression=70, recovery=35) расходится с зонами шагов; 25.08 — обратный
случай (−8%): план недооценил ту же сессию.

Интервальные шаблоны (справочно, середина зоны — нижняя оценка): stored
60.0-86.4 TSS/ч vs zone-implied 28.4-47.9 TSS/ч; 16.08 Neuromuscular
Sprints: план 30.0 TSS vs зоны 14.2 TSS (факт 14.7) — тот же паттерн.

## Вердикт

`VALIDATED` — плановый TSS лёгких вело систематически завышен относительно
зон собственного воркаута; фактический TSS станок-сессий совпадает с
зонами (±7%), а не с планом (+23-37%). Атлет исполняет предписание верно.

## Границы доказанного

Доказано для steady-state вело-шаблонов (endurance/progression/recovery) на
материале одного плана (checkpoint #119, FTP 172). Не доказано для
интервальных шаблонов (нужна NP-оценка) и для бега/плавания (другие
методики факта). Численные дельты зависят от FTP атлета; знак и порядок
дельты — от структуры зон и `_TARGET_DENSITY`, т.е. устойчивы.

## Рекомендация

1. Согласовать `_TARGET_DENSITY` в `models/workout_catalog.py` с
   zone-implied плотностями билдеров: endurance 55→40, recovery 35→22,
   progression 70→45 (значения уточнить тестом на канонических структурах).
2. Добавить регрессионный тест: для каждого steady-state билдера
   zone-implied плотность в пределах density-границ каталога, а
   материализованная `tss_per_hour` ≈ zone-implied (±10%).
3. Пересобрать план после фикса (TSS лёгких дней честно снизится) и
   перепроверить «план vs факт» на следующих станок-сессиях.

## Перенос и очистка

- Что станет обычным тестом: консистентность `_TARGET_DENSITY` и зон билдеров.
- Что переносится в продукт: согласованные значения плотности каталога.
- Что остаётся исследовательским артефактом: `evidence.py` (анализ локальной
  БД; полезен для повторной проверки после фикса, продуктом не импортируется).
- Что удалено: ничего (внешних записей не создавалось).
