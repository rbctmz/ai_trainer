## 🔴 Критично (баги данных / безопасность)

### 1. Дублирование методов в `data/database.py` — мёртвый и опасный код

`save_activities` определён дважды (`data/database.py:347` и `:434`),
`clear_all_data` — дважды (`:494` и `:649`). Python молча перекрывает первый
вариант вторым.

- Первая `save_activities` (`:359`) делает
  `df.to_sql('activities', conn, if_exists='replace')` — **полное удаление
  таблицы при каждом сохранении**. Она мёртвая (перекрыта), но её наличие
  вводит в заблуждение и создаёт риск, если кто-то переупорядочит методы.
- Первая `clear_all_data` (`:494`) не чистит `sleep_data`, `daily_health`,
  `training_status`, `planning_checkpoints` — неполная семантика.

**Действие.** Удалить дубликаты, оставить одну каноничную реализацию каждого
метода. Добавить тест, проверяющий, что `clear_all_data` действительно обнуляет
все реальные таблицы БД: `activities`, `hrv_data`, `sleep_data`, `daily_health`,
`training_status`, `user_settings`, `planning_checkpoints`. (Список взят из
`init_tables` в `data/database.py:98`.) Замечание: `_TRAINING_STATUS_COLUMN_TYPES`
описывает колонки таблицы `training_status`, а не набор таблиц — на него
опираться некорректно.

### 2. SQL-инъекции (f-string в запросах)

`data/database.py`: `get_activities` (`:370`), `get_sleep_data` (`:919`),
`get_daily_health` (`:945`), `get_training_status_history` (`:971`) собирают
запрос через f-string:

    query = f"SELECT * FROM activities WHERE date >= '{cutoff_date}' ORDER BY date DESC"

Сейчас `cutoff_date` вычисляется из `datetime.now()`, поэтому не
эксплуатируемо, но это прямое нарушение собственного правила безопасности, и
при первом же рефакторинге, принимающем пользовательский ввод, станет дырой.
Соседний `get_hrv_data` (`:394`) уже использует параметризованный `?` — надо
унифицировать.

**Действие.** Перевести все четыре запроса на `params=(...)`. Тест в
`tests/test_hrv_data_display.py:106` тоже копирует уязвимый паттерн —
поправить. Тест на контракт должен проверять **поведение**, а не наличие
символа `?` в строке: корректно отрабатывает запрос с «опасным» значением
даты (например, `'2020-01-01'; DROP TABLE activities; --`) и возвращает
ожидаемые строки, не выполняя побочных эффектов. Идея в том, что параметризация
доказывается результатом, а не литеральным совпадением в исходнике.

### 3. `shell=True` в `fix_dependencies.py:14`

`subprocess.run(cmd, shell=True, ...)` где `cmd` собирается из аргументов.
Скрипт описан в `CLAUDE.md` как «run `python3 fix_dependencies.py`».

**Действие.** Передавать список аргументов без `shell=True`, либо удалить
скрипт целиком — его функциональность перекрыта `scripts/doctor_env.py repair`.

## 🟠 Высокий приоритет (надёжность / архитектура)

### 4. Фабрика провайдеров создаёт все инстансы на каждый вызов

`AIProviderFactory.get_available_providers()` и `get_first_available()`
(`models/ai_providers.py:587`, `:612`) инстанцируют **все** провайдеры при
каждом вызове — включая сетевые пробы Ollama (`client.list()`) и Gemini. При
рендеринге AI-страницы это вызывается многократно → латентность и побочные
сетевые эффекты.

Это не только гигиена: это наблюдаемая пользователем задержка и лишние
сетевые пробы на каждый ререндер, поэтому вынесено перед `print`-cleanup.

**Действие.** Кэшировать результат в `StateManager` (как уже сделано для
`ai_coach`/`ai_tools`) либо сделать фабрику stateful-синглтоном с TTL-кэшем
доступности.

### 5. `print()` в production-коде вместо логгера — 114 случаев

Концентрация в `data/garmin_client.py` (~30 `print("DEBUG: ...")`),
`models/ai_providers.py` (инициализация провайдеров пишет в stdout),
`services/sync.py`. В `garmin_client.py` уже заведён `garmin_logger`, но он
используется вперемешку с `print`. DEBUG-вывод в stdout засоряет
Streamlit-консоль и неуправляем.

**Действие.** Использовать единый `utils/logger.py`, заменить `print` на
`logger.debug/info/warning`. Для AI-провайдеров — silent-init по умолчанию
(паттерн `GoogleGeminiProvider(emit_warnings=...)` уже есть, распространить на
остальные).

### 6. Bare `except:` глотают всё, включая `KeyboardInterrupt`

`models/ai_coach_universal.py:145`, `:233`, `models/ai_data_context.py:217`,
`models/ai_providers.py:351`, `utils/modern_ui.py:580`, `:678`.

**Действие.** Заменить на `except Exception:` с осмысленной обработкой и
логированием.

### 7. Слишком крупные файлы

### 9. Тип-ошибки в сигнатурах

`models/ai_providers.py`: `Dict[str, any]` (lowercase) во всех
`test_connection` / `get_available_models` — должно быть `Any`. Сейчас `any` —
это built-in функция, не тип; mypy/pyright пометит.

### 10. `Settings` читается один раз при импорте

`config/settings.py` — все атрибуты class-level через `os.getenv` в момент
импорта. Нет reload, нет валидации. Смена `.env` требует рестарта; невалидные
значения (например `USER_FTP=abc`) упадут только в рантайме `int(...)`.

**Действие.** Вынести валидацию (хотя бы `try/except ValueError` с понятным
сообщением) или dataclass с `field(default_factory=...)`. Опционально —
`Settings.reload()`.

### 11. `clean_value` импортирует pandas/numpy в теле метода

`data/database.py:78` — `import pandas as pd` внутри
`@staticmethod clean_value`, вызывается для каждого значения каждой строки
синхронизации. Незначительно по времени, но неоправданно.

**Действие.** Поднять импорты на уровень модуля (pandas уже импортирован
сверху файла).

### 12. Магические константы AI-вызовов

`max_tokens=1000`, `temperature=0.7` захардкожены в каждом провайдере. Для
coaching-сценариев 1000 токенов часто обрезают длинный план.

**Действие.** В `Settings` — `AI_MAX_TOKENS`, `AI_TEMPERATURE` с дефолтами;
передавать в провайдеры.
