Этот ExecPlan поддерживается по `.agent/PLANS.md`. Задача [#636](https://github.com/rbctmz/ai_trainer/issues/636). Текущий согласованный scope — методология и документация; следующие UI-реализации перечислены как план, а не запущены автоматически.

## Purpose / Big Picture

Агент должен уметь начать UI-задачу с понятной пользовательской цели, выбрать существующие компоненты, показать проверяемый сценарий и передать результат без выдумывания доменной логики. Пользователь должен оценивать рабочее взаимодействие до дорогой реализации. Доказательство текущего docs-среза: из AGENTS/workflow можно дойти до карты экранов, brief и конкретного примера Today; проверки не конфликтуют с существующими A/B/C и ролями.

## Milestones and Plan of Work

M0 — текущий docs-срез. Supervisor/Spec Owner сводит два аудита, оформляет стандарт и интеграцию. Входы: код/действующие правила/решения владельца; выход: этот пакет, brief и docs PR. Проверки: локальные ссылки, diff, read-only review, отсутствие runtime changes. Оценка карты экранов и визуального направления может уточняться в следующих конкретных задачах; это не блокирует сохранение основы.

M1 — пилот Today в #634/#635 или его согласованном продолжении. UI Specialist получает актуальные DTO, brief из `workflow.md` и выбранные владельцем сценарии. Выход: минимальный интерактивный вариант с визуальным состоянием, тренировками и предложением, без нового набора метрик; перечень покрытых и непокрытых состояний. Использовать существующий showcase/изолированные fixtures. Acceptance: понятность основного действия, один индикатор, честная неопределённость, корректный выбор без записи, мобильное раскрытие. Сначала проверить доступность данных для after-workout/partial brick; если их нет, передать точный контрактный пробел Spec/Domain роли. Класс определить по фактическому изменению, не наследовать C автоматически.

M2 — стабилизировать общие patterns после пилота. UI Specialist сверяет потребителей выбранных metric/session/proposal/disclosure components и переносит повторяемые решения в общие компоненты. Вход: конкретно принятые решения M1, не абстрактная новая тема. Выход: typed fixture gallery и документированные варианты плотности. Acceptance: отсутствие регрессий потребителей, keyboard/focus, contrast light/dark, 390/1280 и дополнительные layout проверки. Отдельные backend поля не добавлять попутно.

M3 — отдельные bounded slices Обзора, Плана и Коуча. Начать с сравнения сегодняшнего контекста Today/Обзор на одном снимке; затем основной просмотр/изменение Плана; затем ориентация и контекст Коуча. Для каждого собственные task, brief, states и проверки. Не объединять в «редизайн всего приложения». Выход: проверенные пользовательские пути и обновлённая карта, без альтернативных решений на разных экранах.

M4 — закрепить повторяемость. Supervisor собирает фактические затруднения владельца, незапланированные повторные правки и используемые компоненты; если галерея/brief не помогают, упростить их. Нет цели вводить количественный KPI без baseline. Новый CI visual gate обсуждать только после воспроизводимого класса регрессий.

## Concrete Steps and Validation

Рабочая копия текущего docs-среза: `/Users/gregkisel/.codex/worktrees/design-workflow/ai_trainer`. Перед продолжением выполнить `git status --short --branch`, проверить HEAD и issue/PR. Для docs diff достаточно `git diff --check` и проверки существования относительных Markdown-ссылок изменённых docs; не запускать live API/DB или web build ради текста. Проверить список изменённых файлов: только AGENTS и docs.

Для будущего UI-пилота выполнять актуальные команды проекта: `npm --prefix web run lint`, затем `npm --prefix web run build`, затем релевантные изолированные E2E. Build и E2E не запускать одновременно из-за общей `.next`. При изменении DTO использовать действующую contract freshness процедуру. Ни один passing test не объявлять результатом пользовательского тестирования.

Reviewer получает точный diff и критерии, возвращает воспроизводимые findings; один consolidated review и delta-check следуют существующему бюджету. Проверка владельцем содержит fixture/версию, задачу, наблюдение без подсказки и явный outcome; персональные данные в публичный PR не включаются.

## Idempotence and Recovery

Docs-проверки read-only и повторяемы. Новые документы и ссылки обратимы обычным git diff/revert в своей ветке; чужой checkout и PR #635 не изменяются. При смене базы перепроверить ссылки и источники аудита, сохраняя датированный срез. Новая реализация не стартует только из-за наличия M1–M4 в плане.

## ASR / risk traceability

Сохраняются ASR-MOD-2 (UI не владеет domain semantics), ASR-REL-2 (неопределённость явная), ASR-SEC-1 (нет секретов/персональных данных в примерах), ADR-0001 (web primary, Streamlit fallback). Никакой статус ASR не переводится в green этим docs-срезом; runtime тактики не меняются. Отдельный ADR не нужен для переиспользования текущих инструментов.
