# Дизайн внутри AI SDLC

Этот процесс дополняет [канонический workflow](../AI_Feature_Development_Workflow.md), не заменяет классы риска, контракты, review budget или полномочия ролей. Цель — проверить смысл интерфейса до дорогой реализации, а не добавить отдельную цепочку approval.

## Последовательность и роли

1. **Постановка.** Назначенный Spec / Architecture Owner фиксирует пользовательскую задачу, границы экрана, acceptance и non-goals в существующей задаче. Для локального UI-fix это могут быть уже заданные условия — не требуется новый агент/документ. Supervisor классифицирует scope по действующим правилам.
2. **Проработка.** UI / Design Specialist описывает первый взгляд, раскрытие, действие и затронутые состояния, опираясь на реальные DTO. Он выбирает компоненты и визуальное представление внутри согласованных критериев. Пробел контракта передаёт Spec/Domain роли, а не заполняет предположением в TypeScript.
3. **Прототип.** Для нового/существенно изменённого взаимодействия делает минимальный интерактивный пример на синтетических данных. Использует реальные presentational components, существующий showcase или изолированную acceptance-поверхность. При неопределённой композиции сравнивает два варианта; для очевидной локальной правки это избыточно. Прототип не сохраняет реальный план и не вызывает live providers.
4. **Оценка.** Для значимой новой структуры показать владельцу конкретный сценарий: что здесь происходит, что он сделает и что ожидает после действия. Записать наблюдения и выбранное решение. Уже выраженное согласие не запрашивать повторно. При отсутствии ответа продолжать независимую подготовку; не считать молчание приёмкой. Если договорённость с владельцем нужна для конкретного решения — остановить только зависимую часть, а не всю работу.
5. **Реализация.** Обычные SpecDD/BDD/TDD/Contract First применяются по классу. Prototype не обходит contract gates и не переносит расчёты из Python в UI. Документ и код обновляются вокруг итогового решения, а не истории всех попыток.
6. **Проверка и передача.** Автор проверяет сценарии, reviewer — named criteria и затронутые общие компоненты; Supervisor собирает точную версию, screenshots, команды, ограничения и outcome владельца. Непроверенное называется непроверенным. Merge — по существующим полномочиям, без отдельного нового design gate.

Передача между ролями содержит: цель и границу, файлы/DTO, что уже проверено, конкретный недостающий вход и критерий завершения. Название модели не назначает роль. Luna можно поручать ограниченный аудит, вариант brief или проверку зафиксированного примера; доступ к коду не даёт права на самовольное изменение acceptance/семантики.

## Соразмерность

| Класс | Достаточный design-артефакт | Проверка |
|---|---|---|
| C: обратимая локальная стилистика/docs | Короткая заметка: проблема, scope, ожидаемый вид, проверка; по месту в task/PR | Targeted visual/docs check; для UI screenshot, relevant narrow viewport/keyboard checks. Для docs UI build не нужен |
| B: новый/изменённый пользовательский поток | Brief и релевантная матрица в существующих acceptance; прототип для нового/существенно меняющегося взаимодействия, иначе существующая поверхность с пометками или fixture | RED→GREEN для observable behavior, lint/build для web, релевантные UI/E2E, визуальная оценка |
| A: доменная/контрактная/системная граница | UI-сценарии в существующем ExecPlan и slice spec; не второй параллельный spec | Все текущие A gates плюс пользовательское представление тех же evidence/identity/eligibility |

Не все случаи автоматически Class C, потому что меняется React/CSS. Если меняются доступность действия, смысл неопределённости, выбор/подтверждение, нужно заново оценить класс. Не требовать тест на каждую статическую подпись; тестировать риск и наблюдаемое поведение. Скриншотный regression test вводить там, где он помогает обнаружить реальный повторяемый дефект, а не для формального покрытия.

## Воспроизводимая среда

Текущий `/showcase` включается build-time `NEXT_PUBLIC_SHOW_DEV_TOOLS=true`; он использует статические типизированные fixtures и не должен становиться копией domain logic. Сегодняшние E2E используют временные базы и свои порты. Для будущего пилота расширить showcase состояниями реальных компонентов и одной явной точкой входа; не делать временный proxy единственным способом передачи дизайна.

Любой пример содержит fixture/scenario id, версию кода, размер viewport, тему и метку синтетических данных. Установить, какие действия являются только выбором, какие имитированы и какие отключены. Примеры с персональными данными не прикладывать к публичному issue/PR. Сравнение с чужим приложением фиксировать через общий паттерн, без копирования приватных значений, credentials или screenshot аккаунта.

## Пилот Today: заполненный brief

Задача: утром понять тренировки и необходимость действия; после тренировки увидеть относящийся к ней факт и оценку. Граница: ежедневное исполнение и конкретное предложение; долгосрочная динамика остаётся в Обзоре. Связанные задачи #610, #634, PR #635. Пилот — будущая реализация, текущий пакет docs не утверждает её завершение.

Сначала видны состояние сейчас и тренировки дня. Крупный индикатор восстановления сопровождается статусом и свежестью; показателевая панель не заполняется метриками лишь ради симметрии. Факторы раскрываются рядом с индикатором. У отклонения остаётся краткое предупреждение; у доступного предложения видны варианты и последствия. После выполнения обратная связь относится к конкретной сессии. До переноса блока наверх проверить серверный контракт нескольких prompts.

Использовать TodayReadiness / TodaySession / TodayDecisionStory, pending proposal preview и существующую feedback-проекцию из `web/lib/types.ts`; поля сверить на HEAD пилота. Пока не доказана доступность личной нормы/направления всех сигналов, прототип не обещает «сегодня против обычно». Пробелы передать Domain/API с конкретным полем и сценарием. Плохой сон при нормальной готовности — отдельный вопрос расчёта, не лицензия сочинить UI-объяснение.

| Fixture | Вид и действие | Инвариант проверки |
|---|---|---|
| ordinary | Одна тренировка, один индикатор, подробности по запросу | Нет лишнего выбора/дублированного score |
| two_sessions | Две самостоятельные тренировки | Не выдуманы время и связь |
| brick / partial_brick | Связанные этапы и переход; факт по доступным данным | Не соединены разные группы; часть не названа целым |
| stale / missing / conflicting | Значение и ограничение видимы вместе | Старое/неизвестное не названо свежим или безопасным |
| proposal_available | Выбор, было/станет, точная кнопка | Выбор не пишет; подтверждение адресует выбранный вариант |
| no_proposal / stale_proposal | Проблема и честное отсутствие применимого предложения | Нет фиктивного активного подтверждения |
| completed / ambiguous_match | Результат/ответ для известной сессии либо уточнение связи | Нет произвольного присвоения feedback |
| loading / empty / error | Понятное состояние и путь восстановления | Ошибка не выглядит как день отдыха |

Это перечень дизайна и проверок, не утверждение, что все fixtures уже есть. В #635 покрыта часть ordinary/multi-session/brick/proposal/freshness/error сценариев; partial brick, полноценный after-workout путь и реальный день остаются открыты.

Проверка владельцем: без подсказки назвать тренировку, понять ограничение данных, найти предложение, предсказать действие кнопки. Фиксировать конкретное затруднение и число подсказок; не выдумывать universal KPI по одному человеку. Успех пилота — отсутствие непонятых критических действий в согласованных сценариях и явная запись владельца о результате. Это UX-outcome, не замена тестов/CI.
