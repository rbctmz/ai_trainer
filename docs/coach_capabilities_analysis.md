# AI-коуч: что умеет сейчас и куда расширять

> Дата: 2026-06-28 · Автор: Claude (Cowork) · Контекст: web-миграция, ветка `feat/web-migration`
> Связано с: [#11 Polish Coach web UI](https://github.com/rbctmz/ai_trainer/issues/11), `docs/competitive_analysis_intervalcoach.md`
> Метод: разбор кода (`models/ai_tools.py`, `ai_coach_runtime.py`, `api/routers/coach.py`) + реальная сессия `chats/afe2437c.json` («Что ты можешь?», 28.06) + референс IntervalCoach Coach+.

---

## TL;DR

Коуч — это **read-only аналитик прошлого**. Он отлично объясняет «что произошло и почему» по 19 инструментам над фактическими данными Garmin, и после рефактора `fbeb259` честно завершает ответ (двухпроходный синтез после инструментов). Но у него есть один структурный провал, который вылез прямо в живой сессии: **коуч не видит план подготовки**, который пользователь только что собрал в Planning. Он буквально отвечает «плана в моих данных нет», хотя план лежит в `planning_checkpoints`. Плюс он обещает действия, которых не может выполнить («я составлю тебе план»), и даёт нутрициологические цифры из общих знаний LLM, не из базы.

Самое ценное расширение — не новые экраны, а **дать коучу видеть и трогать то, что продукт уже умеет считать**: активный план, единые сигналы восстановления, и (с одобрением) запуск/корректировку плана. Это превращает его из «комментатора» в «второго пилота».

---

## 1. Что коуч умеет сейчас

**Архитектура чата (после `fbeb259`):**
1. Скрытый первый проход — LLM выбирает инструменты (`[TOOL: ...]`).
2. Инструменты выполняются, в UI летят чипы `tool_call`.
3. Второй проход — LLM синтезирует финальный ответ из результатов инструментов (стримится по токенам).
4. Системный синтез-промпт запрещает «вернусь позже» и черновики.

**Сильные стороны:**
- **Мульти-провайдерность** (DeepSeek по умолчанию, плюс OpenAI/Anthropic/Gemini/Ollama/Mock) — нет vendor lock-in, есть offline и demo.
- **Живой стриминг** + markdown-рендер (таблицы/жирный) в вебе.
- **19 инструментов** с реальным доступом к данным, без галлюцинаций цифр.
- **Tool-call прозрачность** — видно, какие инструменты дернулись.
- **История чатов** персистится (файлы `chats/*.json`).

**Инвентарь инструментов (все read-only):**

| Группа | Инструменты |
|---|---|
| Активности | `get_activities`, `get_recent_activities`, `get_activity_stats`, `get_activity_by_sport`, `get_activities_by_date_range`, `calculate_weekly_stats`, `find_best_performances` |
| Нагрузка (PMC) | `get_performance_metrics` (CTL/ATL/TSB), `analyze_training_load`, `compare_periods` |
| Восстановление | `get_hrv_data`, `analyze_hrv_trends`, `analyze_recovery_state` |
| Сон | `get_sleep_data`, `get_sleep_stats`, `analyze_sleep_patterns` |
| Статус/здоровье | `get_training_status`, `analyze_training_status`, `get_daily_health_stats` |

Всё это — про **прошлое и настоящее по факту**. Ни одного инструмента про **план/будущее** и ни одного **пишущего** инструмента.

## 2. Разбор реальной сессии (`chats/afe2437c.json`)

Пользователь спросил «Что ты можешь?» → «Распиши возможности» → «Проверить динамику за месяц» → **«Ты видишь мой план подготовки?»**.

**Что было хорошо:**
- Корректный разбор формы: TSB −26.1, ATL 48 vs CTL 22, статус Garmin PRODUCTIVE, сравнение недели (327 vs 355 TSS среднее).
- Честность про пробелы: «данных по readiness нет», «без HRV летишь вслепую».
- Хорошая структура: краткий вывод → рекомендации → следующий шаг.
- Динамика за месяц через `compare_periods`: +30 тренировок, +22.9ч, +1201 TSS.

**Что вскрылось как проблема:**

1. **🔴 Коуч слеп к плану.** На прямой вопрос — «твоего плана подготовки в моих данных нет... плана как файла ты мне не передавал». **Это неправда на уровне продукта:** план есть в `planning_checkpoints` (его строит страница Planning). Коуч просто не имеет инструмента его прочитать. Для пользователя это выглядит как «правая рука не знает, что делает левая».

2. **🔴 Обещает то, что не может.** «Я могу расписать тебе план на 2 недели прямо сейчас», «скажи цель — составлю план с периодизацией». Но у коуча нет инструмента ни собрать план (это делает `training_planner`/`/api/planning/build`), ни сохранить его. Он сгенерит прозу, которая никуда не попадёт и не свяжется с Planning. Разрыв ожидания.

3. **🟡 Противоречие по данным.** Коуч несколько раз говорит «HRV нет / readiness нет», хотя HRV в системе есть (дашборд показывает 27–32). Либо инструмент не вызвался, либо окно последних дней пустое — но пользователю это читается как ненадёжность.

4. **🟡 Нутрициология из воздуха.** Конкретные цифры (1.6–2 г белка/кг, 4–5 г углеводов/кг, «20–30 г белка в течение часа») — это общие знания LLM, не из проверяемой базы. Местами разумно, но не помечено как «вне базы» и не сослано на источник.

5. **🟢 Многословность.** Ответы очень длинные; «что я умею» расписано на простыню. Это вопрос промпта/UX (#11).

## 3. Референс: что умеет Coach в IntervalCoach (Coach+/Coach Mode)

Из `docs/competitive_analysis_intervalcoach.md` и публичных источников, их чат-коуч:

- **Tool-calling с мутациями под одобрение** — коуч может *предложить* изменить сегодняшнюю тренировку, пользователь видит «Workout Proposed» и approve/reject. У нас мутаций нет вообще.
- **Memories с context-тегами** — заметки об атлете (sport, intensity, day-of-week, indoor/outdoor, срок годности), semantic retrieval по контексту вопроса, еженедельная дедупликация. У нас память = плоская история сообщений.
- **Единый signals engine** как источник правды для чата, дашборда и daily cron (HRV suppression streak, RHR elevation, ACWR, monotony, durability). У нас коуч считает по сырым CTL/ATL/TSB.
- **Recovery profile / personal recovery curve** (Max-тариф) — персональный half-life восстановления по типам стимула.
- **Daily briefing** — проактивное «вот твой сегодняшний план/выводы», а не только реактивный чат.
- **Peer comparison / benchmarks** — соц-слой (нам не нужен).

Ключевой архитектурный урок их changelog: **половина их багов — рассинхрон «дашборд говорит одно, чат другое»**. У нас та же ловушка уже проявилась (коуч не видит план). Лечится единым контрактом данных — это перекликается с тем, что Codex делает в #9/#10.

## 4. Что добавить — приоритизированно

### 🔴 P0 — закрыть структурный разрыв «коуч ↔ продукт»

**4.1. Инструмент «прочитать активный план».** Новый tool `get_active_plan` в `ai_tools.py` поверх `restore_goal_plan_from_checkpoint(db.get_latest_planning_checkpoint())` — возвращает цель, дату старта, фазы, недельные TSS-таргеты, ближайшие сессии, прогноз TSB. Тогда на «видишь мой план?» коуч ответит по факту. **Это самый дешёвый и самый заметный фикс** — переиспользует уже готовый `api/planning_service.py`.

**4.2. Инструмент «ближайшие тренировки из плана».** `get_upcoming_workouts(days=7)` — что план ставит на ближайшие дни (вместо «плана нет» давать «завтра по плану лёгкое вело 20 TSS»). Дашборд это уже умеет (`next_days`), коуч — нет.

**4.3. Чинить «HRV нет».** Проверить, почему коуч не видит HRV: окно дней в `get_hrv_data`, формулировка в промпте. Возможно, добавить в синтез-промпт правило «если инструмент вернул данные — не говори, что их нет».

### 🟡 P1 — от «комментатора» к «действию» (под одобрение)

**4.4. Approval-gated мутации.** Коуч *предлагает* действие → пользователь подтверждает в UI → выполняется. Минимум два действия, оба уже есть в `api/planning_service.py`:
- «Собрать план к цели X к дате Y» → `build_plan(...)` (нужно собрать цель/дату/часы через уточняющие вопросы).
- «Скорректировать неделю» → `apply_adjustment(...)`.

Это убирает разрыв из п.2 (обещает → теперь реально делает) и повторяет проверенный паттерн IntervalCoach. **Важно:** мутации только через explicit confirm, никогда автоматически.

**4.5. Единый signals engine как tool.** Когда у бэкенда появится `signals` (это прямо тема #10 — explicit state contracts), дать коучу `get_signals()` вместо самостоятельного вывода из сырых метрик. Один источник правды для дашборда и чата → нет противоречий.

### 🟢 P2 — глубина и доверие

**4.6. Память об атлете с тегами.** Профиль/предпочтения/ограничения (травмы, доступные дни, цель) сверх плоской истории. Расширить `chat_manager.py` или новый `models/coach_memory.py`. Сейчас каждый чат стартует «с нуля».

**4.7. База знаний для нутри/физиологии.** Чтобы цифры белка/углеводов были из проверяемого источника, а не из LLM. Либо помечать такие куски как «общая рекомендация, вне данных», либо подключить курируемую KB (по образцу Blocks). Минимум — дисциплина в промпте: «нутрицифры помечай как ориентир».

**4.8. Daily briefing.** Проактивный экран/сообщение «как ты сегодня и что делать» поверх того же `get_active_plan` + сигналов. Превращает реактивный чат в ежедневную точку входа.

**4.9. Подрезать многословность.** В синтез-промпт: «3–5 ключевых пунктов, без простыней; детали — по запросу». Это и часть #11 (читабельность длинных ответов).

## 5. Рекомендация по последовательности

| Шаг | Что | Где | Зависимость |
|---|---|---|---|
| 1 | `get_active_plan` + `get_upcoming_workouts` (read) | `models/ai_tools.py` + `planning_service` | нет — можно сразу |
| 2 | Фикс «HRV/readiness нет» | промпт + проверка окна tool | нет |
| 3 | Подрезать многословность | синтез-промпт | нет (часть #11) |
| 4 | Approval-gated «собрать/скорректировать план» | coach tools + UI confirm | UI-слой #11 |
| 5 | `get_signals()` как единый источник | после signals engine | #10 |
| 6 | Память с тегами, KB, daily briefing | новые модули | стратегически |

**Самый высокий ROI прямо сейчас — шаг 1.** Один read-only инструмент над уже готовым `planning_service` убирает самый заметный конфуз («коуч не видит мой план») и логически связывает два главных экрана продукта — Coach и Planning. Всё остальное строится поверх.

Шаги 4–5 осознанно идут после бэкенд-слайсов Codex (#9 payload-семантика, #10 state-контракты), чтобы коуч и UI опирались на единый контракт, а не на эвристики.
