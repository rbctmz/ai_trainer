# M4c: «Изменить план» — компактный stepper (черновик для утверждения)

Это черновик спеки среза M4c issue [#304](https://github.com/rbctmz/ai_trainer/issues/304): «„Изменить план“ организует существующие параметры в компактный stepper/drawer: 1) подход и цель, 2) доступность, 3) нагрузка и preview, 4) подтверждение». Живёт по правилам `.agent/PLANS.md` и `docs/AI_Feature_Development_Workflow.md`; реализация начинается после утверждения и мержа M4b ([#336](https://github.com/rbctmz/ai_trainer/pull/336)).

## Purpose / Big Picture

Сейчас «Собрать план»/«Изменить план» — это одна длинная форма в `web/app/planning/page.tsx` (BuildMode): все поля и кнопка «Предпросмотр плана» на одной странице. M4c перестраивает тот же поток в компактный пошаговый stepper из четырёх шагов, не теряя ни одной существующей возможности: режимы «К старту / Развивать форму / Ручные фазы», горизонт, события Intervals.icu (read-only), источник рекомендаций «по вашим данным / по умолчанию», preview → confirm. Первый план и редактирование активного плана идут по одному пути.

Важные свойства из #304: stepper гидратируется один раз и не затирает правки при SWR-ревалидации; keyboard/mobile-поток проходит все шаги; browser acceptance 1280/390 без body overflow; event-goal без подтверждённой A-гонки блокирует переход дальше понятным сообщением; training-goal не получает выдуманную дату/тейпер.

## Что уже есть (факты из кода)

- BuildMode — единая форма в `web/app/planning/page.tsx` (секции: подход/цель/дата/горизонт/намерение/фазы/события, доступность, режим нагрузки + WeeklyTargetPreview, «Предпросмотр плана», подтверждение с `confirmPlan`).
- Hydrate-once уже реализован: `hydrated` ref + `revalidateOnFocus: false` — форма заполняется из `/api/onboarding/planning` ровно один раз.
- `BasisChip` уже показывает источник рекомендаций: «по вашим данным / по умолчанию».
- «Изменить план» сейчас просто переключает вкладку на `build` (тот же BuildMode); префилл идёт из сохранённого профиля, а не из активного checkpoint.
- Уроки M3: браузерный рантайм не активирует нативный `<summary>` клавиатурой — для шагов stepper используем button-backed элементы с `aria-current`/`aria-expanded`-семантикой.
- Отдельных компонентов планирования нет (`web/components` их не содержит) — всё живёт в page.tsx (2100+ строк).

## Scope (in scope)

1. **Stepper из 4 шагов** (вместо одной длинной формы), шаги ровно по #304:
   1. «Подход и цель» — режим, тип цели, дистанция, дата A-старта (только для «К старту»), горизонт, намерение, ручные фазы, события Intervals.icu (read-only).
   2. «Доступность» — часы в неделю, доступные дни.
   3. «Нагрузка и preview» — режим нагрузки, WeeklyTargetPreview, кнопка «Предпросмотр плана».
   4. «Подтверждение» — сводка preview (изменение TSS, план недель, forecast), «Подтвердить и сохранить».
2. **Навигация и валидация между шагами**: индикатор шагов, «Назад»/«Далее», `aria-current` на активном шаге, перенос фокуса на заголовок шага; «Далее» блокируется на шаге 1 для event-goal без подтверждённой A-гонки с понятным сообщением.
3. **Редактирование активного плана**: при `has_plan` и клике «Изменить план» stepper предзаполняется из активного checkpoint (те же входы, что у плана), а не из профиля; путь первого плана остаётся как есть (гидратация из онбординга один раз).
4. **Power-user и честность**: три режима сохраняются; ручные фазы, горизонт и read-only события не убираются; источник рекомендаций виден на шаге 3.
5. **Микроcopy**: переиспользуем существующие русские labels, новых смешанных RU/EN строк не добавляем (не дублируем #268).

## Отклонение от «без бэкенда»

В ходе реализации выяснилось: `status.checkpoint` — это компактная сводка, а не входы для формы, а маппить русские labels цели/дистанции в браузере нельзя (доменное правило). Поэтому добавлен один маленький read-only контракт `GET /api/planning/edit-context` — сервер отдаёт входы активного checkpoint в виде, который ждёт форма (English goal/distance keys, weekday keys, availability, events, demand). Остальные API не менялись.

## Non-goals

- Других бэкенд/API-изменений нет: stepper потребляет `/api/planning/edit-context`, `/api/planning/target-preview`, `/api/planning/build`, `/api/onboarding/planning`, `/api/planning/status`.
- Drag-and-drop календарь, автоматическая публикация в Intervals.icu, изменение формул нагрузки, дневные лимиты.
- Новые UI-framework или chart-зависимости (урок #267: только CSS/layout repair).

## BDD / acceptance

- Given сохранённый профиль, When открывается stepper (первый план), Then шаг 1 заполнен ровно один раз из онбординга; правки атлета не затираются при SWR-ревалидации.
- Given активный план, When атлет жмёт «Изменить план», Then stepper открывается на шаге 1 с входами активного checkpoint (цель, доступность, режим), а не профиля.
- Given event-goal без подтверждённой A-гонки, When атлет жмёт «Далее», Then переход заблокирован и показано понятное сообщение; training-goal не получает выдуманную дату/тейпер.
- Given шаг 3, When атлет меняет режим нагрузки или доступность, Then preview обновляется и показывает источник рекомендаций; «Предпросмотр плана» остаётся явной кнопкой.
- Given шаг 4, When атлет подтверждает, Then сохраняется план (существующий `confirmPlan`-путь), вкладки обновляются, активный план виден в Обзоре.
- Given keyboard, When атлет проходит шаги Tab/Enter, Then фокус следует за шагами, активный шаг объявлен (`aria-current`); на 1280 и 390 px нет body overflow.
- Source-гейты: page.tsx (или компонент stepper) содержит заголовки четырёх шагов, «Назад»/«Далее», `aria-current`, «Предпросмотр плана», «Подтвердить и сохранить».
- Smoke (`python -m pytest tests/smoke -q`), Next lint/build зелёные.

## Дизайн-решения и открытые вопросы

### D1: stepper или drawer (нужно решение)

**Вариант А (рекомендую): stepper-вкладка.** «Изменить план» открывает шаги прямо в контенте вкладки (как сейчас build). Проще для keyboard/mobile, не требует overlay-семантики, фокус-ловушек.

**Вариант Б: drawer.** Компактнее визуально, но сложнее доступность (focus trap, закрытие по Esc, aria-modal) и лишний оверлей на 390px.

### D2: префилл при редактировании (нужно решение)

**Вариант А (рекомендую): из активного checkpoint.** «Изменить план» начинает с реальных входов плана — меньше сюрпризов при пересборке.

**Вариант Б: из профиля (как сейчас).** Меньше кода, но редактирование может «забыть» то, что в checkpoint.

### D3: структура файлов (нужно решение)

**Вариант А (рекомендую): вынести BuildMode/stepper в `web/components/planning/PlanBuilder.tsx`.** page.tsx уже 2100+ строк; вынос улучшает читаемость (ASR-MOD-2) и повторяемость; source-гейты обновляются.

**Вариант Б: оставить в page.tsx.** Меньше churn, но страница растёт дальше.

### D4: issue-контракт (нужно решение)

**Вариант А (рекомендую):** GitHub issue «M4c: „Изменить план“ — компактный stepper» (parent #304, refs #300/#267) с `### ExecPlan`, `### Acceptance criteria`, `### Smoke baseline`.

**Вариант Б:** без отдельного issue, сразу PR.
