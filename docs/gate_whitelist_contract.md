# Gate Whitelist Contract — coach narrative evidence gate

> Конечный контракт для `coach_narrative_evidence_gate`.
> **Правило:** гейт принимает только явно перечисленные и протестированные формы;
> всё остальное блокируется по умолчанию (fail-closed).
> Источник: локальная wiki Григория `concepts/gate-whitelist-pr515.md`; согласовано в PR #515.

## Инварианты (не нарушать)

1. **Одна метрика = один evidence-домен.** Никогда не удовлетворяй claim по метрике A evidence'ом домена B (напр. темп — power-доменом, нагрузка-тренд — одним `compare_periods` для сессии).
2. **Каждый субъект в составном утверждении требует своего evidence.** `Темп и мощность...` — оба; `Темп и пульс...` — оба; `HRV и нагрузка...` — оба. Если для любого пропал — блок.
3. **Исторический тренд ≠ будущее.** Явный future-маркер (`следующая`, `предстоящая`, `на следующей неделе`) ограничивает *свою* клаузу, не отменяет историческое утверждение с ней в одном предложении.
4. **Longitudinal (тренд) требует longitudinal-доказательства.** Одна comparable-session пара НЕ доказывает «растёт/улучшается» по месяцам/неделям.
5. **Сравнение валидно только с явной попарной формой** («по сравнению с прошлой»), и сравниваемый объект — **тоже сессия**. «по сравнению с прошлым месяцем/неделей/периодом» → это longitudinal, не pair.
6. **Fail-closed при неоднозначности.** Несколько session-компараторов, которые нельзя однозначно привязать к target → блок (`TREND_COMPARATOR_MISSING`).
7. **Завершённое время = историческое.** `получилась/была/оказалась/вышла` + `следующая` → исторический факт (если нет явного future-глагола), а не план.

## Whitelist поддерживаемых форм (A–G)

> Каждая форма = { форма утверждения, evidence domain, обязательный comparator, правила направления }.

### A. Попарная сессионная форма (PAIRWISE SESSION)
- **Форма:** `<метрика> тренировки <дата?> по сравнению с прошлой(предыдущей) улучшился/улучшилась/снизился...`
- **Evidence domain:** `session_pace | session_power | session_hr` (строго по метрике)
- **Comparator:** `get_comparable_session` с той же метрикой; ровно один однозначно привязанный к target
- **Направление:** delta знак согласован с утверждением (улучшился = позитивный сдвиг)
- **Fail-closed:** если >1 компаратор не привязывается, или метрика другой домен
- **Регрессии:** `Темп тренировки 2026-08-20 по сравнению с прошлой улучшился.`

### B. Составная сессионная форма (COMPOUND SESSION)
- **Форма:** `<метрика1> и <метрика2> тренировки по сравнению с прошлой улучшились`
- **Evidence domain:** все названные метрики (`session_pace AND session_power`, `session_pace AND session_hr`)
- **Comparator:** отдельный для каждой метрики, однозначно привязанный
- **Fail-closed:** если хоть одна метрика без подтверждающего компаратора
- **Регрессии:** `Темп и мощность тренировки...`, `Темп и пульс тренировки...`

### C. Longitudinal-тренд (TREND — период/обобщённое)
- **Форма:** `<субъект> на тренировках растёт/улучшается/выросла` · `<метрика> выросла/улучшается`
- **Evidence domain:** `trend_*` (HRV-тренд, load-тренд, pace-тренд по периоду)
- **Comparator:** `compare_periods` (агрегат по периоду) **или** ≥3 независимых session-наблюдений по РАЗНЫМ датам/периодам (одна пара НЕ доказывает тренд)
- **Направление:** согласовано с заявленным трендом
- **Fail-closed:** <3 независимых наблюдений по разным датам/периодам (в т.ч. одна comparable-session пара) → блок; отсутствие компаратора → блок
- **Регрессии:** `Темп на тренировках растет.` · `Нагрузка: выросла` · `Нагрузка — выросла` · `HRV: улучшается` · `Нагрузка, судя по данным, выросла`

### D. Исторический тренд при наличии будущей клаузы
- **Форма:** `<исторический тренд>, <а затем/потом/далее/после этого> <future-факт>`
- **Разделители:** запятая, `но`, `затем`, `потом`, `далее`, `после этого`
- **Правило:** историческое утверждение валидируется само по себе; future-клауза не отменяет его и не прикрывает отсутствие компаратора
- **Регрессии:** `Текущая нагрузка снизилась, а на следующей неделе будет 403 TSS.` · `...на следующей неделе будет 403 TSS.` · `Текущая нагрузка снизилась, затем на следующей неделе будет 403 TSS.`

### E. Период-синонимы longitudinal (LONGITUDINAL PERIOD)
- **Форма:** `по сравнению с прошлым/предыдущим/предшествующим месяцем(неделей/периодом)`
- **Evidence domain:** longitudinal (НЕ одна comparable-session пара)
- **Fail-closed:** одна пара не доказывает `улучшился`
- **Регрессии:** `Темп на тренировках по сравнению с предыдущим месяцем улучшился.` · `...с прошлым месяцем...`

### F. Завершённая «следующая тренировка» (COMPLETED NEXT)
- **Форма:** `Следующая тренировка <была/получилась/оказалась/вышла> лучше(хуже) прошлой`
- **Evidence domain:** session (попарно, прошедшее время / завершённый вид)
- **Fail-closed:** если нет явного будущего глагола → историческое, требует компаратора; без компаратора → блок
- **Регрессии:** `Следующая тренировка была лучше прошлой.` · `Следующая тренировка получилась лучше прошлой.`

### G. Плановые/будущие утверждения (PLANNED/FUTURE — вне evidence)
- **Форма:** `На предстоящей неделе нагрузка вырастет.` · `Следующая тренировка будет лучше прошлой.`
- **Evidence domain:** не требуется (это план/прогноз, не факт о прошлом)
- **Meaning:** гейт не блокирует явное будущее; но НЕ маскирует исторические утверждения (см. D)

### F vs G — явный различитель
> Единственный решающий признак между формой F и G — **presence/absence будущего глагола**.
> - **Есть future-глагол** (`будет`, `вырастет`, `станет`) → **G** (план/прогноз, вне evidence, не блокируется).
> - **Нет future-глагола** + завершённый вид (`была/получилась/оказалась/вышла`) → **F** (историческое, требует компаратора, иначе блок).
> Если future-глагол присутствует, форма автоматически относится к G — никогда к F.

## Явно вне whitelist (→ fail-closed)

- Любые формы, не перечисленные выше — **fail-closed (блок)**.
- Агрегатный `compare_periods` как доказательство одиночной сессии (pace/power) — запрещено (см. Инвариант 1, кейс «Темп по сравнению с прошлой тренировкой»).
- Великодушие с тенсом: обобщённый `следующ*|предстоящ*` без явного future-глагола/маркера.
