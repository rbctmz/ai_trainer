## Purpose / Big Picture

Сегодня веб-интерфейс AI Trainer (каталог `web/`, Next.js) вырос до **десяти равноправных пунктов навигации**, накопленных по принципу «одна фича = один экран за одну issue». Владельцу «стыдно отдать продукт тестеру»: навигация не помещается на экран, часть поверхностей — это research-инструменты, а дневная петля пользователя размазана и дублируется между экранами.

Цель этого плана — привести интерфейс к **связной информационной архитектуре под первую бету**, НЕ переписывая содержимое экранов. «Информационная архитектура» здесь означает просто: сколько верхнеуровневых дверей видит пользователь и как они сгруппированы.

Прицел беты (решение владельца, зафиксировано в Decision Log): **технические атлеты-тестеры, локальная установка через Docker**, первичный источник данных — **Intervals.icu** (а не Garmin), потому что Intervals агрегирует много марок устройств (Garmin, Wahoo, Polar, Coros, Suunto), и тестер с любым устройством сможет участвовать. Перевод источника данных и деплой — отдельные треки (см. `docs/self_hosted_deployment_execplan.md` и трек service-readiness); ЗДЕСЬ мы делаем только UI-связность, которая и есть причина «стыдно».

Что человек сможет увидеть после этого плана (наблюдаемый результат):

- Открыв веб-приложение на экране шириной 1280px, он видит навбар из **не более чем 4 primary-пунктов** — «Сегодня», «Обзор», «План», «Коуч» — без горизонтального скролла и без обрезанных пунктов.
- Он НЕ видит по умолчанию три research/shadow-поверхности (страница «Восстановление», страница «Решения», inline-блок «Прогноз качества сессии · shadow» на «Сегодня») — они спрятаны за флагом и включаются только для разработки.
- Поверхности «раскладки сырых данных» (HRV, Сон, Активности) достижимы как детальные вкладки внутри «Обзор», а не как отдельные верхние пункты.
- «План vs факт» больше не отдельный пункт: сверка «план против факта» живёт вкладкой внутри «План».
- Включив демо-режим (тумблер в навбаре), тестер видит **связный населённый продукт** по всем четырём primary-поверхностям, не касаясь реальных данных владельца.

Термины, используемые ниже, в простом языке:

- **readiness (готовность)** — суточная оценка 0–100, насколько организм готов к нагрузке; показывается почти на каждом экране.
- **TSB / CTL / ATL** — стандартные метрики тренировочной нагрузки (баланс формы, длительная и краткосрочная нагрузка). Для этого плана важно лишь, что они выводятся плиткой на многих экранах.
- **shadow / research-поверхность** — экран или блок, помеченный как «наблюдение, не влияет на решения»; это инструмент для накопления научных данных, а не функция для пользователя.
- **reconciliation / «план vs факт» / adherence** — сопоставление запланированных сессий с фактически выполненными активностями.
- **демо-режим** — режим, в котором чтение/запись идут в отдельную изолированную SQLite-базу (`ai_trainer_demo.db`), чтобы реальная база владельца (`ai_trainer.db`) не пострадала. Включается тумблером «Демо» в навбаре, который через `web/lib/api.ts::setDemo` пишет флаг в `localStorage`; после этого фронт сам дописывает `?demo=1` к API-запросам. Просто `?demo=1` в адресной строке страницы демо НЕ включает.

Работа разбита на четыре независимо проверяемых среза, каждый со своей GitHub issue: **#253** (навбар 10→4), **#254** (флаг для shadow-поверхностей), **#255** (слить adherence в «План»), **#256** (оживить демо-данные).

## Decision Log

- Decision: целевая навигация — ровно 4 primary-пункта: «Сегодня», «Обзор» (переименование «Дашборд»), «План», «Коуч».
  Rationale: дневная ментальная петля атлета — «как я → что делать → сделал ли → что скажет коуч» — покрывается этими четырьмя. Остальные шесть поверхностей либо дриллдауны сырых данных (HRV/Сон/Активности), либо дубли (План vs факт), либо research (Восстановление/Решения). 10 равноправных дверей — главный источник ощущения перегруза.
  Date/Author: 2026-07-21 / Claude Code (по итогам живого обхода, согласовано с владельцем).

- Decision: research/shadow-поверхности НЕ удаляем, а прячем за фронт-флагом `NEXT_PUBLIC_SHOW_DEV_TOOLS` (по умолчанию выкл).
  Rationale: эпизоды/снимки восстановления должны копиться дальше (научная ценность), а session-quality forecast остаётся как evidence. Пользователю-тестеру их видеть незачем и они создают пустые/непонятные состояния. Флаг — обратимо и дёшево. Механизм `NEXT_PUBLIC_*` выбран потому, что в `web/` пока нет никакого пути серверного конфига до клиента, а build-time public-переменная Next.js — самый простой первый шаг.
  Date/Author: 2026-07-21 / Claude Code.

- Decision: «План vs факт» (adherence) сливается в «План» вкладкой; отдельный пункт навбара убирается, маршрут `/adherence` остаётся рабочим для прямых ссылок.
  Rationale: тот же домен уже живёт во вкладке «Скорректировать» внутри `/planning` и полосами на `/today`. Три входа в один смысл — дубль. Не ломаем deep-link, чтобы не пришлось чинить внешние ссылки.
  Date/Author: 2026-07-21 / Claude Code.

- Decision: направление беты — локальный Docker у каждого тестера, Intervals.icu как первичный источник. Это фиксируется как контекст, но САМА реализация источника/деплоя ВНЕ scope этого плана.
  Rationale: текущая архитектура одно-пользовательская насквозь; локальный single-tenant совпадает с ней и не требует auth/мультитенанта (это шаг 2 трека service-readiness, недели работы). Intervals-primary обходит худший блокер (неофициальный логин Garmin) и расширяет круг устройств тестеров. Но эти работы — отдельные issue; здесь только UI-связность.
  Date/Author: 2026-07-21 / Claude Code (направление — решение владельца).

Навигация задаётся в `web/components/Nav.tsx` — там массив `links` из 10 объектов `{ href, label }`, отрисованный в одну строку. Именно этот массив и его контейнер правит срез #253.

Слой API — `api/` (FastAPI). Веб ходит в него через rewrites (`web/next.config.mjs`), проксируя `/api/*` на бэкенд. На БЭКЕНДЕ демо-режим резолвится в `api/deps.py::get_database` по query-параметру `?demo=1`, который направляет чтение/запись в отдельную базу `ai_trainer_demo.db` (см. `api/deps.py` и `services/acceptance_mode.py`). Но САМ ВЕБ не включается URL-параметром: демо активируется тумблером «Демо» в навбаре, который через `web/lib/api.ts::setDemo` пишет флаг в `localStorage`, после чего `web/lib/api.ts::withDemo` дописывает `?demo=1` ко всем API-запросам. Эндпоинты демо — `POST /api/demo/seed` и `POST /api/demo/clear` (роутер `api/routers/system.py` смонтирован с префиксом `/api`, НЕ `/api/system`); сам сидинг — `services/demo_mode.py::activate_demo_mode(state)`.

Единый источник меток «план vs факт» на фронте уже есть — `web/lib/adherence.ts`; его надо переиспользовать, а не плодить второй (важно для #255).

Флаг `SHOW_DEVELOPMENT_TOOLS` существует как backend-переменная окружения (см. `config/settings.py` и CLAUDE.md), но до фронтенда `web/` он не доходит; отдельного клиентского флага нет (важно для #254).

## Idempotence and Recovery

Правки навбара, флага и вкладок — чисто аддитивные и обратимые правкой тех же файлов; повторный прогон шагов безопасен. Демо-сидинг идемпотентен по построению: он пишет только в изолированную `ai_trainer_demo.db`, а `demo/clear` возвращает её в чистое состояние; реальная `ai_trainer.db` не затрагивается ни на каком шаге (изоляция — в `api/deps.py::get_database` и `services/acceptance_mode.py`). Если какой-либо milestone провалился на полпути, откат — `git checkout` затронутых файлов; ветки и worktree'ы держать по правилу репо (issue → ветка → PR).
