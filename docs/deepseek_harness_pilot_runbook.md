# DeepSeek Harness pilot runbook

Пилотный контур для issue-класса **B** с ролью **Implementer (Domain / API)**.
DeepSeek Harness официально значится **developer preview**, поэтому нулевой
квалификационный прогон обязателен, а версия закреплена.

## Роли и границы

| Участник | Роль | Что делает | Чего не делает |
| --- | --- | --- | --- |
| DeepSeek Harness | Implementer (Domain / API) | правит код и тесты в изолированном worktree, коммитит локально | не пушит, не открывает PR, не мержит, не трогает UI/спеки/ADR |
| Supervisor (человек) | Supervisor / Integrator | проверяет дерево, воспроизводит тесты, пушит, открывает PR, мержит | — |
| Codex | Independent Reviewer | один consolidated full-diff review по PR | не правит код |

Причинность результата не размывается: на первом пилоте ровно два вендора
(DSH реализует, Codex проверяет). OpenCode подключается отдельным пилотом.

## Неподвижные правила

1. **Версия закреплена:** `dsh 0.1.0-rc.6`. Обновление во время эксперимента
   запрещено — иначе качество harness не отделить от качества модели.
2. **DSH не путается с `git push`:** способность выполнить внешнее действие не
   измеряет качество реализации и добавляет гонку мержа.
3. **Проектный `.env` не участвует.** DSH fail-closed отказывается читать
   `DEEPSEEK_BASE_URL` из `.env` проекта: ключ и endpoint передаёт
   запускающее окружение. Поэтому пилот идёт в worktree **без** `.env`.
4. **Отдельный `DSH_HOME`** (временный), чтобы настройки личного профиля и
   ранее сохранённые сессии не влияли на результат.
5. **Платный модельный вызов — только по явному разрешению владельца.**
   Подготовка preflight бесплатна (материализация профиля и `--dump-config`
   модель не вызывают).
6. **Первым идёт read-only smoke** без изменений в дереве.
7. **Один агент на ветку.** Параллельные сессии на одной ветке уже приводили к
   мержу без ведома владельца (PR #572), это исключается.

## Preflight

```bash
# 1. изолированный worktree без проектного .env
git worktree add --detach /tmp/dsh-pilot-wt main

# 2. бесплатная подготовка: версия, worktree, DSH_HOME, профиль, наличие кред
scripts/dsh_pilot_preflight.sh

# 3. один read-only smoke — только после разрешения владельца
DEEPSEEK_API_KEY=<из окружения, не из файла> \
DSH_PILOT_PROMPT=scripts/dsh_pilot_smoke_prompt.txt \
scripts/dsh_pilot_preflight.sh --smoke --allow-paid-call
```

Промпт smoke версионирован (`scripts/dsh_pilot_smoke_prompt.txt`), поэтому его
SHA-256 попадает в метрики и постановки задач остаются сопоставимыми. Промпт
read-only: он требует только чтения файлов и ответа по фактам.

Preflight проверяет: закреплённую версию; отсутствие `.env` и чистоту worktree;
материализацию профиля `headless` в отдельном `DSH_HOME`; наличие
`DEEPSEEK_API_KEY` в окружении (значения не печатаются); модель и permission
mode профиля. Режим `smoke` дополнительно требует `--allow-paid-call`.

Свежий `DSH_HOME` даёт дефолты профиля: `provider: deepseek-official`,
`model: deepseek-v4-flash`, `apiKeyEnv: DEEPSEEK_API_KEY`,
`DSH_PERMISSION_MODE=workspace-write`. Личный профиль (`~/.dsh`) в пилоте не
используется.

## Read-only smoke: что он должен доказать

Smoke — это квалификация harness, а не оценка кода. Промпт формулируется как
read-only задача (прочитать файлы, ответить по фактам, ничего не менять), а
скрипт после прогона проверяет `git status --porcelain` в worktree: любое
изменение означает провал smoke.

Минимальные критерии прохождения:

- `dsh --profile headless` стартует и завершается сам, без хуков и webhook;
- финальный ответ печатается, процесс возвращает `0` только при нормальном
  завершении;
- сессия сохранена в `$DSH_HOME/sessions`;
- дерево worktree после прогона не изменилось;
- метрики собраны (см. ниже).

Callback-механизм для первого пилота не нужен: контроллер просто ждёт процесс и
читает его вывод. Входящий webhook не подходит — он запускает сессию
fire-and-forget и не сообщает о завершении; ACP/JSON-RPC понадобятся только
постоянному исполнителю.

## Метрики

Обычные процессные метрики — те же, что у Class A/B записей в
`docs/engineering_process_metrics.md`: lead/cycle time, раунды ревью, P0/P1 и
blocking P2, escaped defects, CI-ретраи и flakes, follow-up P2, wait time.

Экспериментальные метрики пилота (собирает `dsh_pilot_preflight.sh`):

| Поле | Источник |
| --- | --- |
| `dsh_version`, `profile` | preflight |
| `starting_sha` | worktree перед прогоном |
| `prompt_sha256` | SHA-256 файла промпта (сопоставимость постановок) |
| `duration_seconds`, `exit_code` | измерение процесса |
| `tokens_input` / `tokens_output` / `tokens_cache_read` / `tokens_reasoning` | сумма записей `usage` в `session.jsonl.zstd` |
| `tool_calls`, `steps` | записи `tool/call`, `step/end` |
| `human_messages_in_session` | записи `user/message`; значение > 1 означает вмешательства человека |
| `worktree_clean_after` | `git status` после прогона |
| `cost` | не собирается без таблицы цен — фиксируется как `not captured` |

Метрики нужны, чтобы отделить качество harness от качества модели и качества
постановки задачи. Без них сравнение с Class A/B записями некорректно.

## Критерии завершения пилота

- acceptance criteria выбранной issue закрыты, scope не расширен;
- RED→GREEN подтверждён числами, а не формулировками;
- ревью-бюджет ≤ 2 нативных раунда, находки отвечены письменно;
- 0 escaped P0/P1;
- evidence отделяет проверенное локально от непроверенного;
- запись пилота добавлена в `docs/engineering_process_metrics.md` вместе с
  экспериментальными метриками.

Выбор issue: подходящий bounded Class B follow-up берётся **только** из
подтверждённых находок ревью (например, из PR #574) или из отдельного
триажа с воспроизведённым дефектом. Искусственно придумывать задачу ради
пилота нельзя.
