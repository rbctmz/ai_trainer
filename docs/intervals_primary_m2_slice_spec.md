# M2 Slice-Spec: онбординг параметров планирования → первый план (#271)

- Status: НА ПРИЁМКЕ — код M2 начинается после принятия §10
- Related: `docs/intervals_primary_handoff_execplan.md` (Milestone M2), M1 (#270, merged),
  ExecPlan-предшественник по UI — `docs/ui_consolidation_beta_execplan.md`
- Архитектура: без изменений. M1 наполнил `activities` из Intervals; M2 добавляет
  недостающий вход — параметры атлета, из которых строится ПЕРВЫЙ план.

## 1. Что уже есть (разведка, 2026-07-25)

Прежде чем спорить о scope — факты о текущем коде:

- **Механика сборки плана готова.** `web/app/planning/page.tsx::BuildMode` собирает ВСЕ
  нужные входы (подход/intent/цель/дистанция/часы/дни/demand/события) и умеет
  `preview → confirm(persist=true)`; `api/planning_service.py::build_plan` (291) и
  `POST /api/planning/build` (`api/routers/planning.py:157`) — рабочий контракт с
  409-гейтом «сначала preview, потом сохранение».
- **`/today` уже умеет пустоту.** `api/today_snapshot.py:244` → state `no_plan`,
  action `open_planning`; `GET /api/planning/plan` → `has_plan:false`. То есть «план
  виден на `/today`» — СЛЕДСТВИЕ persist, отдельной работы не требует.
- **Онбординга в web нет вообще.** В `web/app/` нет ни роута, ни компонента; единственная
  welcome-поверхность — легаси-Streamlit `ui/pages/welcome.py`, и она Garmin-центрична
  (логин/демо), про планирование в ней нет ничего.
- **Параметры планирования НЕ персистятся.** Персистится только `demand`
  (`user_settings`, `api/planning_service.py:149/162`), а `goal_type`/`distance` косвенно
  оседают в checkpoint'е (`models/planning_checkpoints.py:253`). Часы, дни недели,
  режим и intent живут только в React-стейте: каждый вход на `/planning` начинается с
  жёстких дефолтов `hours=10`, `days=все 7`.
- **Дефект, который M2 обязан убрать: молчаливая выдуманная A-гонка.** UI стартует в
  режиме `event_goal` и подставляет `defaultEventDate()` = сегодня+56 дней
  (`web/app/planning/page.tsx:111`). Сервер честно требует подтверждённую A-гонку
  (`build_plan`: `raise ValueError("event_goal requires a confirmed A event")` → 422), но
  до этой ошибки дело не доходит: UI сам подставил дату. Тестер без гонки получает
  восьминедельный план с тейпером под событие, которого не существует, и никакого
  сигнала об этом. Это ровно тот класс дефекта, который мы зафиксировали у конкурента
  (план от дефолтного FTP=250 без проверки профиля): не «агент ошибся», а
  **молчаливый дефолт вместо честного вопроса**.

Вывод: M2 — это не «написать форму». Форма есть. M2 — это **сделать входы явными,
персистентными и честными**, и дать первому входу маршрут.

## 2. Scope / Non-goals / Definition of Done

**В объёме M2:**

1. **Персистентный профиль планирования** — режим/intent/цель/дистанция/часы/дни
   (demand уже персистится, подключается к тому же профилю). Один источник правды для
   `/planning`, будущего коуча и M3-handoff.
2. **API-контракт профиля** — чтение/запись + `completed`-признак + `suggested`-дефолты,
   выведенные ИЗ ДАННЫХ атлета (§5), а не из констант.
3. **Graceful `event_goal` без A-гонки** — детерминированный резолвер: нет
   подтверждённой A-гонки (или Intervals недоступен) → предлагается `training_goal` +
   `intent=develop`; фиктивная дата не подставляется НИКОГДА. 422 от сервера
   становится недостижимым по нормальному пути, но остаётся как fail-closed.
4. **Первый вход в web** — онбординг-поверхность, которая ведёт от «активности есть,
   плана нет» к `build_plan(persist=True)` и показывает результат на `/planning` и `/today`.
5. RED-матрица §6.

**Вне объёма M2 (осознанно):**

- **Синк НЕ строит план сам** (из формулировки #271: «честный „увидел свой план"»).
  План требует явных входов атлета; автопостроение по одному факту синка — это ложное
  обещание и оно же ломает decision-журнал.
- Wellness/readiness-часть онбординга — M4 (#273).
- Source-agnostic тексты и Docker-quickstart — M3 (#272).
- Правки самого алгоритма планирования (фазы/рампы/микроциклы) — не трогаем.
- Legacy-Streamlit `ui/pages/welcome.py` — не переносим (правило CLAUDE.md: новое
  product-поведение не идёт в `ui/pages/*`).

**Definition of Done:**

- Тестер с активностями из M1 и пустым планом проходит онбординг → `get_active_plan(db)`
  отдаёт план; `/planning` показывает активный checkpoint; `/today` уходит из `no_plan`.
- Повторный вход на `/planning` предзаполнен сохранённым профилем, а не константами.
- Атлет без A-гонки доходит до плана без единого ручного трюка и без выдуманной даты.
- `python -m pytest -m "not live and not debug" tests/` зелёный (база 1199).

## 3. Профиль планирования — контракт хранения

Ключ `planning_profile` в существующей таблице `user_settings` (JSON-документ). Почему
не новая таблица: аддитивно, без миграции, ровно один потребитель, а `user_settings` уже
несёт planning-состояние (`demand`). Схема таблиц не трогается — значит и rollback
тривиален (удалить ключ).

```
planning_profile = {
  "planning_mode": "event_goal" | "training_goal" | "manual",
  "intent":        "maintain" | "develop",
  "goal_type":     <как в build_plan>,
  "distance":      <как в build_plan>,
  "available_hours": float,
  "available_days":  ["mon", ...],
  "horizon_weeks":   int,
  "updated_at":      ISO-8601,
  "source":          "onboarding" | "planning_form"
}
```

Новый модуль `api/planning_profile.py`: `load_profile(db)`, `save_profile(db, payload)`,
`profile_status(db)`. Валидация **fail-closed и переиспользует существующие whitelist'ы**
`build_plan` (режим/intent), а не заводит вторые: неизвестное значение → `ValueError` →
422, битый/недописанный JSON в `user_settings` → профиль считается отсутствующим
(`completed=false`), а не роняет страницу.

`demand` НЕ дублируется в профиль — остаётся под своим ключом; профиль на него ссылается
через существующий геттер. Два места хранения одного факта — источник рассинхрона.

## 4. API-контракт

```
GET  /api/onboarding/planning   → {completed, profile|null, suggested, event_context}
PUT  /api/onboarding/planning   → {completed: true, profile}          # 422 на невалидное
```

- `completed` — профиль сохранён и валиден.
- `suggested` — предложение системы (§5), всегда присутствует; клиент вправе его
  переписать целиком.
- `event_context` — `{has_a_race, events[], source, degraded_reason|null}`: результат
  §5-резолвера, включая честное «Intervals недоступен» вместо пустого списка.

Роутер `api/routers/onboarding.py`, подключается в `api/main.py`. Эндпоинт **не строит
план** — построение остаётся на существующем `POST /api/planning/build` (persist+confirm).
Разделение намеренное: профиль — это вход, план — это решение с checkpoint'ом и журналом;
склеивать их в один вызов значит потерять preview-гейт 409.

## 5. Предложение вместо выдумывания (ядро среза)

Функция `suggest_planning_defaults(db, *, today)` в `api/planning_profile.py`:

| Поле | Откуда берётся | Fallback |
|---|---|---|
| `available_days` | дни недели с активностями за последние 4 недели | все 7 |
| `available_hours` | медианная недельная длительность за 4 недели, округлённая вниз до 0.5 | 10.0 |
| `goal_type`/`distance` | доминирующий спорт истории (`sport` в `activities`) | `triathlon`/`olympic` |
| `planning_mode` | `event_goal` ⟺ найдена подтверждённая A-гонка, иначе `training_goal` | `training_goal` |
| `intent` | `develop` | — |

Каждое предложенное поле сопровождается `basis`: `"derived"` (посчитано по истории) или
`"fallback"` (данных не хватило). UI обязан показать basis — атлет должен видеть, что
именно система знает, а что домыслила. Это тот же паттерн `confidence + reasons + floors`,
который мы отметили как образцовый в разборе конкурента.

**Резолвер A-гонки** `resolve_event_context(*, days=365, today)`:

- Intervals отдал события → A-гонки = `priority == "A" and confirmed is not False`
  (та же семантика, что уже применяет `toggleEvent` в UI).
- Есть хотя бы одна → `has_a_race=true`, `planning_mode="event_goal"`.
- Ноль A-гонок → `has_a_race=false`, `planning_mode="training_goal"`,
  `degraded_reason=null` (это НЕ деградация, это нормальный сценарий).
- `IntervalsICUError`/нет ключа → `has_a_race=false`, `planning_mode="training_goal"`,
  `degraded_reason="<текст>"` — поток не падает (issue: «не роняет поток»), но причина
  видна и в API, и в UI.

`defaultEventDate()` из `web/app/planning/page.tsx` **удаляется**. Дата события задаётся
только явно — выбором обнаруженного события или ручным вводом при осознанно выбранном
`event_goal`.

## 6. Обязательные RED-матрицы M2

| Гейт | Что доказывает |
|---|---|
| M2-T1 | round-trip профиля: `PUT` → `GET` возвращает то же; повтор идемпотентен; `updated_at` двигается |
| M2-T2 | fail-closed валидация: неизвестный `planning_mode`/`intent`/день недели → 422, профиль в БД не изменился |
| M2-T3 | битый JSON под ключом `planning_profile` → `completed=false`, 200, страница жива (не 500) |
| M2-T4 | `suggested` выводится из истории: сид активностей пн/ср/сб → `available_days=[mon,wed,sat]`, `basis="derived"`; пустая БД → fallback + `basis="fallback"` |
| M2-T5 | нет A-гонки → `planning_mode="training_goal"`, `has_a_race=false`, НИ ОДНОЙ подставленной даты в ответе |
| M2-T6 | `IntervalsICUError` → 200 с `degraded_reason`, а не 503; поток онбординга продолжается |
| M2-T7 | сквозной: профиль → `build(persist,confirm)` → `get_active_plan` не None → `/api/planning/plan` `has_plan=true` → `/api/today` state ≠ `no_plan` |
| M2-T8 | изоляция: весь сценарий на временной БД, live-база не затрагивается (правило M1-ревью) |

Все — `tests/smoke/`, реальная `Database`, без обращений к сети (Intervals-клиент
подменяется на уровне сервиса).

## 7. Web-поверхность

`/planning` в состоянии «плана нет» рендерит онбординг-карточку «Соберём первый план»:
предложенные значения из §5 с пометкой basis, пять полей, кнопка → preview → «Сохранить».
После сохранения карточка исчезает, форма продолжает работать как сейчас, но
предзаполняется профилем.

Почему не отдельный роут `/onboarding`: навигацию только что консолидировали (issues
#253–#256, закрыты 2026-07-22), и добавлять шестой пункт меню ради одноразового экрана —
шаг назад. Пустое состояние `/planning` — уже то место, куда `/today` шлёт действием
`open_planning`. Альтернатива вынесена в §10 D1 как решение владельца.

## 9. Риски

- **Главный:** правки `BuildMode` задевают рабочий preview/confirm-контур (409-гейт,
  `base_checkpoint_id`). Митигируется тем, что §7 добавляет обёртку и предзаполнение, а
  не переписывает `requestPayload()`/`confirmPlan()`.
- Вывод `available_hours` из истории может дать нереалистично низкое значение атлету,
  который только начал синк (2 недели данных). Митигация: `basis="derived"` показывается
  явно, значение редактируемо, при <14 днях истории — принудительный `fallback`.
- Rollback: удалить ключ `planning_profile` и вернуть онбординг-карточку под флаг —
  схема БД не менялась, `build_plan` не менялся.

## 10. Решения (ждут владельца)

- **D1 — где живёт онбординг.** Рекомендую: пустое состояние `/planning` (§7).
  Альтернатива — отдельный роут `/onboarding` с редиректом с `/today`; дороже на пункт
  навигации, но лучше читается в M3-quickstart («открой /onboarding»).
- **D2 — хранение профиля.** Рекомендую `user_settings.planning_profile` (JSON, §3).
  Альтернатива — отдельная таблица `planning_profile` с колонками; дороже (миграция),
  выигрыш только если профиль станет мультипользовательским (это шаг 2 SaaS-лестницы,
  не сейчас).
- **D3 — предложенные дефолты.** Рекомендую вывод из истории с `basis` (§5).
  Альтернатива — статические константы как сейчас; дешевле, но сохраняет ровно тот
  молчаливый дефолт, который M2 и должен убрать.
- **D4 — автопостроение плана после синка.** Рекомендую НЕ делать (§2 non-goals),
  как и сформулировано в #271.
