# AI Feature Development Workflow

Ты — senior software engineer и AI coding agent.

Работаем в режиме:
- SpecDD
- BDD
- TDD
- Contract First
- Self-Review
- Minimal Complexity

---

# ГЛАВНЫЕ ПРАВИЛА

Сначала думай.  
Потом планируй.  
Только потом пиши код.

Не начинай продуктовую реализацию сразу.

Всегда:
1. анализируй существующую архитектуру
2. изучай текущий код
3. проверяй существующие паттерны
4. переиспользуй текущие решения
5. минимизируй изменения

Нельзя:
- выдумывать API
- выдумывать библиотеки
- ломать существующую архитектуру
- делать overengineering
- создавать абстракции без необходимости
- менять код вне задачи
- добавлять зависимости без причины

# EVIDENCE DISCIPLINE

Для каждого причинно-следственного тезиса — в ExecPlan, ревью или выводе коуча —
разделяй три уровня:

- **Observed**: наблюдаемый факт и его источник;
- **Inferred**: гипотеза и дешёвая проверка, способная её опровергнуть;
- **Verified by**: реально выполненная проверка и результат, либо `NOT YET`.

Полная нормативная форма и заполненный пример находятся в
`.agent/PLANS.md` → `Evidence Discipline`.

**Minimal disproof before claim:** до того как назвать что-либо багом, корневой
причиной или причинным механизмом, сформулируй и выполни одну дешёвую проверку,
которая могла бы опровергнуть гипотезу. Планируемая проверка не считается
верификацией: пока она не выполнена, пиши `Verified by: NOT YET`. Перед
закрытием задачи повтори релевантную проверку на финальном дереве.

Для пользовательского вывода коуча эквивалентная runtime-граница реализована в
`models/ai_coach_runtime.py`: наблюдение отделяется от вывода, а нехватка или
конфликт данных не заменяются правдоподобной историей.

# REPO-SPECIFIC ARCHITECTURE GUARDRAILS

Для AI Trainer миграция ещё в процессе:
- `web/` + `api/` — основной вектор новых продуктовых изменений
- `services/`, `models/`, `data/` — источник бизнес-логики
- `app.py`, `ui/`, `state/manager.py` — legacy Streamlit fallback, а не целевая поверхность для новых фич

Если задача затрагивает user-facing product flow:
1. сначала зафиксируй spec
2. потом опиши/обнови API contract
3. потом покрой backend behavior тестами
4. потом реализуй shared Python logic
5. только потом подключай `web/`

Не делай:
- новые продуктовые фичи только в Streamlit
- дублирование бизнес-логики между Streamlit и web/API
- перенос доменных правил в frontend-only код без необходимости

# WORKFLOW

Следуй pipeline:

```text
КРАТКАЯ ПОСТАНОВКА ПРОБЛЕМЫ
→ [ПРОВЕРОЧНЫЙ ЭКСПЕРИМЕНТ (EVIDENCE-FIRST SPIKE) → ВЕРДИКТ]
→ SPEC
→ BDD
→ TESTS
→ IMPLEMENTATION
→ SELF-REVIEW
→ FIXES
→ FINAL CHECK
```

Квадратные скобки означают необязательную пару «эксперимент → вердикт». Если
существенной неизвестности нет, переходи от краткой постановки проблемы сразу к
SPEC.

Этот pipeline — default для Class A и для Class B с intentional behavior
change. Pure behavior-preserving refactor использует characterization baseline
вместо искусственного RED. Class C использует сокращённый pipeline:

```text
ПРОБЛЕМА И SCOPE → TARGETED DOCS/VISUAL/CONTRACT CHECK → SELF-REVIEW → FINAL CHECK
```

Class C пропускает отдельные SpecDD, BDD и TDD, если не меняет наблюдаемое
поведение или public contract. При таком изменении задача должна быть
переклассифицирована либо применить соответствующие BDD/TDD stages.

# CHANGE CLASSES AND REVIEW POLICY

До начала реализации назначь изменению один `Change Class`. Если классы
пересекаются, выбирай самый строгий. Повтори классификацию при расширении scope:
fast track нельзя использовать как постоянное исключение для выросшей задачи.

## Class A — Full

Полный контур нужен для изменений архитектуры, модели данных, persistent state,
live-sync/provider integration, security, identity/provenance и значительных
рефакторингов. Обязательны:

- issue с acceptance criteria и явными non-goals;
- ExecPlan по `.agent/PLANS.md` и, где применимо, ASR/ADR traceability;
- заполненный `docs/templates/slice_spec_review_template.md`;
- contract-first BDD/TDD и небольшие RED→GREEN slices;
- независимый checker и один итоговый evidence bundle;
- focused и broad tests, а для состояния — lifecycle/reset/rollback probes.

## Class B — Standard

Стандартный контур предназначен для обычной feature/bug работы без триггеров
Class A. Нужны issue, acceptance criteria, актуальные public contracts,
self-review и релевантная проверка. Для intentional behavior change нужен
RED→GREEN. Для pure behavior-preserving refactor допустима уже зелёная
characterization/equivalence baseline с доказательством неизменности
наблюдаемого поведения; нельзя выдумывать failure или implementation-coupled
test. Отдельный spec/docs PR не нужен: короткая спецификация и реализация могут
идти одним PR. Независимый checker обязателен, если реализация раскрыла риск
корректности, надёжности или новый архитектурный стык.

## Class C — Fast track

Ускоренный контур подходит для локальных docs/UI/cosmetic/mechanical изменений,
которые обратимы и не меняют доменные инварианты. Достаточны ясный scope,
минимальный diff, targeted docs/visual/contract check и self-review. ExecPlan не
нужен; отдельные SpecDD, BDD и TDD тоже не нужны без изменения наблюдаемого
поведения или public contract. Fast track не отменяет branch protection,
обязательный CI, проверку контракта или screenshot/GIF для затронутой
UI-поверхности.

## Automatic escalation triggers

Любой из следующих признаков автоматически переводит изменение в Class A,
даже если первоначально оно казалось маленьким:

- data migration или изменение schema/persistence semantics;
- identity or provenance, cursor ownership либо deduplication rules;
- live-provider write, платный внешний вызов или destructive synchronization;
- security boundary, permissions, secrets или personal-data handling;
- irreversible action или rollback, который нельзя доказать дешёвой проверкой;
- новый cross-module public contract или новая архитектурная граница.

## Review severity

Checker обязан назвать severity, evidence и конкретный gate для каждого
finding:

- **P0** — критическая потеря/раскрытие данных, security breach или неуправляемая
  live-запись; всегда блокирует merge.
- **P1** — нарушение корректности, ключевого инварианта, надёжности или public
  contract; блокирует merge.
- **P2** — существенный риск. Блокирует merge, если затрагивает correctness,
  reliability, data, security или contract; иначе допускается только как явно
  назначенный follow-up issue с owner.
- **P3** — cosmetic/maintainability замечание без риска поведения; merge не
  блокирует.

Формат finding: `Severity → Observed → Inferred → Verified by → merge/follow-up
gate`. Предпочтение reviewer не является blocking finding без нарушенного
инварианта или acceptance criterion.

## Review budget

Бюджет — не более **two spec-review rounds**: один консолидированный первичный
review и одна проверка исправлений. Новый раунд допустим, если найден новый
architecture boundary или новые доказательства меняют риск. Иначе после бюджета
нужно явно выбрать исход: исправить blocking finding до merge, сузить scope так,
чтобы нарушение исчезло, либо принять **только non-blocking** риск/создать для
него follow-up issue. Исчерпание review budget никогда не понижает severity и не
разрешает merge с открытым P0/P1 или blocking P2. Бесконечная полировка
non-blocking формулировок не должна задерживать проверяемую реализацию.

# ШАГ 0 — EVIDENCE-FIRST SPIKE (НЕОБЯЗАТЕЛЬНО)

Spike — это короткий воспроизводимый эксперимент, который отвечает на один
дорогой неизвестный вопрос до того, как окончательная спецификация закрепит
непроверенное предположение. Spike не является продуктовой реализацией и не
заменяет SpecDD, BDD, TDD, контрактные тесты или архитектурное решение.

Применяй правило:

> Сначала кратко сформулируй проблему и неизвестное. Если предполагать дороже,
> чем проверить, выполни ограниченный эксперимент. Только затем фиксируй
> окончательную спецификацию.

## Когда spike нужен

Используй spike, когда хотя бы одно из следующего существенно влияет на решение:

- внешний API или SDK документирован неполно либо ведёт себя неоднозначно;
- неизвестен реальный формат или качество данных;
- нужно проверить совместимость двух систем;
- есть риск производительности, конкурентного доступа или миграции;
- выбирается математическая модель, алгоритм или способ хранения данных;
- ошибка предположения приведёт к дорогой переработке нескольких модулей.

## Когда spike не нужен

Не создавай spike, если:

- поведение уже закреплено существующими контрактами и тестами;
- изменение маленькое, обратимое и не содержит существенной неизвестности;
- ответ надёжно следует из текущего кода или официального контракта;
- эксперимент лишь откладывает понятную реализацию;
- spike используется как повод обойти тесты или архитектурную рецензию.

## Сначала краткое описание эксперимента (spike brief)

До одноразового кода зафиксируй в `spikes/issue-NNN-short-name/README.md`:

- вопрос;
- гипотезу;
- наблюдение, которое её опровергнет;
- границы, риски и бюджет эксперимента;
- данные или очищенные фикстуры;
- команду запуска.

Given/When/Then можно использовать для проверки конкретного поведения API, но
это не обязательный формат исследовательского вопроса.

## Вердикт

Эксперимент заканчивается одним из четырёх вердиктов:

- `VALIDATED` — гипотеза подтверждена внутри записанных границ;
- `PARTIAL` — подтверждена только часть гипотезы;
- `INVALIDATED` — наблюдение опровергло гипотезу;
- `INCONCLUSIVE` — данных или качества эксперимента недостаточно для решения.

Ошибка окружения или отсутствие данных не считаются автоматическим
`INVALIDATED`. Всегда перечисляй границы доказанного и то, что эксперимент не
проверял.

## Безопасность и воспроизводимость

- Продуктовый код не импортирует ничего из `spikes/`.
- Не коммить секреты, персональные данные и сырые приватные ответы провайдеров.
- По умолчанию используй временную БД, очищенные фикстуры и запросы только на
  чтение.
- Внешние записи, платные вызовы и реальные данные требуют явного разрешения и
  заранее ограниченного объёма.
- Запиши дату, существенные версии API/библиотек и точную команду запуска.
- Подтверждённое поведение перенеси в обычные тесты или контракты. Сам spike не
  является регрессионной проверкой.
- Неподтверждённый одноразовый код удали либо оставь только как явно помеченный
  исследовательский артефакт.

## Связь с ExecPlan

Для крупной архитектурной задачи оформляй spike как M0 или прототипирующий этап
живого ExecPlan по `.agent/PLANS.md`. Для короткой автономной проверки достаточно
краткого описания эксперимента; если вердикт ведёт к значимой реализации, после
него создай полноценный ExecPlan.

Существенные решения переноси в `Decision Log` ExecPlan и при необходимости в
ADR. ExecPlan должен кратко содержать выводы эксперимента, а не зависеть только
от ссылки или устного контекста.

Полный формат и копируемый шаблон находятся в `spikes/README.md` и
`spikes/TEMPLATE.md`.

# ШАГ 1 — SPEC

Сначала:
- кратко опиши задачу
- сформулируй цель
- перечисли ограничения
- опиши edge cases
- опиши риски
- задай уточняющие вопросы если нужно

Потом:
- предложи минимальный план реализации
- укажи какие файлы изменятся
- укажи возможное влияние на систему

Не пиши продуктовый код до завершения SPEC. Исключение — ограниченный одноразовый
spike после заполнения краткого описания по правилам шага 0.

---

# ШАГ 2 — BDD

Сформируй сценарии поведения в формате:

```gherkin
Given ...
When ...
Then ...
```

Покрой:
- happy path
- edge cases
- failure cases

---

# ШАГ 3 — TDD

Для intentional behavior change сначала создай/обнови тесты. Для pure
behavior-preserving refactor используй characterization/equivalence baseline.
Для Class C без изменения поведения TDD не применяется; выполни targeted check,
указанный в политике класса.

Правила:
- тесты intentional behavior change должны падать до реализации
- тесты должны проверять поведение, а не внутренности
- не писать хрупкие тесты
- покрывать основные сценарии

---

# ШАГ 4 — IMPLEMENTATION

После тестов:
- реализуй минимально необходимое решение
- не добавляй лишнего
- следуй текущему стилю проекта
- сохраняй совместимость
- предпочитай простые решения

При написании кода:
- используй существующие utilities
- используй существующие компоненты
- соблюдай typing
- избегай дублирования
- комментируй только сложную логику

---

# CONTRACT FIRST

Если есть API / DTO / schema:
- сначала опиши контракт
- затем реализацию

Не нарушай:
- типы
- схемы
- backward compatibility

---

# SELF REVIEW

После реализации ОБЯЗАТЕЛЬНО выполни self-review.

Проверь:
- correctness
- edge cases
- race conditions
- performance
- security
- readability
- complexity
- backward compatibility
- dead code
- unnecessary abstractions

Отдельно ответь:
- что может сломаться?
- где слабое место решения?
- как это будет масштабироваться?

---

# FEEDBACK LOOP

После написания кода:
1. запусти тесты
2. исправь ошибки
3. запусти lint
4. исправь warnings/errors
5. проверь типы
6. проверь build

Если что-то падает:
- сначала анализируй
- потом исправляй

Не делай blind fixes.

---

# DEFINITION OF DONE

Задача считается завершённой только если:
- тесты проходят
- lint green
- types green
- build green
- нет явных regression risks
- код соответствует архитектуре проекта

---

# CODE STYLE

Предпочтения:
- readability > cleverness
- explicit > implicit
- simple > abstract
- small functions
- predictable behavior
- минимальная магия

---

# IMPORTANT

Если решение выглядит слишком сложным —
скорее всего оно неправильное.

Всегда сначала предлагай самое простое рабочее решение.
