## Граница и класс

S4 — Class B: представление существующего build-response, без новой схемы,
расчёта нагрузки, provenance/identity или persist semantics. Независимая проверка

получает смысл и критерии; применяет docs/design/README.md и существующие tokens.

## Задача пользователя и первый уровень

Перед сохранением спортсмен должен ответить: **что сохраняется, на какой период,
сколько нагрузки назначено и что произойдёт с текущим циклом**. Подтверждается
сохранённое предложение, а не находящиеся рядом редактируемые поля или старый план.

Сразу доступны состояние предложения; действие новый/изменить; вид подготовки,
дистанция, намерение; фактические начало/конец; применённые события; доступные
дни и часы как потолок; назначенные total TSS за этот период и peak TSS за неделю;
последствие сохранения/замены. Существенный отказ или неизвестность не спрятаны
за раскрытием. «Цель/нед» переименовывается в ориентир нагрузки и не означает,
что каждая неделя достигнет этого числа. Часы доступности не являются назначенными.

В подробностях — недельные нагрузки и единицы, источники/периоды M4, каждый
entry adjustment, применённые ограничения с имеющимися датами и источниками,
модельный прогноз с датированными числами, science audit с его ограничениями.
Технические идентификаторы/версии допускаются только как детали диагностики.
Нельзя заявлять полноту списка ограничений, если DTO её не гарантирует.

## Источники, допустимое представление и пробелы

| Смысл | Источник из сохранённого build-response | Правило / честный fallback |
| --- | --- | --- |
| Действие и последствия | lifecycle.action, closes_cycle_id | start_new ≠ edit_current; закрытие предыдущего только при указанном closes_cycle_id; история/участие не переписываются |
| Цель, подход, намерение | parameters.goal_type/distance/planning_mode/intent | Сведения именно предложения; незнакомое значение обозначить неизвестным, не угадать |
| Период назначений | lifecycle.start_date/end_date | Включительные даты цикла; week_start — метка недели, не замена даты начала |
| События | goal.events; parameters.events — выбранные входы | Показывать применённые события; не превращать внутреннюю goal.event_date в гонку режима training_goal; расхождение не объяснять выдуманной причиной |
| Доступность | parameters.available_hours/available_days | Выбранный потолок; не часы выполненных/назначенных занятий |
| Назначенная нагрузка | totals.total_tss/peak_tss; weeks[].weekly_tss/bike/run/swim | TSS за обозначенный период/неделю; ноль ≠ отсутствие. Не пересчитывать сумму округлённых недель, не включать race_forecast_tss в тренировочные итоги |
| Ориентир | weekly_target + breakdown/demand при наличии | Ориентир отдельно от назначения; объяснение только из breakdown, без сочинённой причины разницы |
| Начальная доза | entry_load, entry_adjustments | Сохранить M4 provenance, покрытие/неизвестность и все изменения; can_publish не сертификат безопасности |
| Ограничения | constraint_application.constraints/protected_dates; entry_load | Показать доступные вид/дату/источник; неизвестные причина/дисциплина/полнота неизвестны; adjustment_note не выдавать за структурированный causal audit |
| Было/станет | preview.total_tss_before/after и weekly_tss_before/after | Нет дат прежнего периода или статуса сравнимости. В S4 v1 **не показывать одиночную дельту/проценты** и не получать старые даты дополнительным текущим GET. В edit честно сообщить отсутствие сопоставимого сравнения, показывать период/итоги кандидата; start_new описать как новый план |
| Физическая доза за весь цикл | В данном response нет полного агрегата назначенных минут/числа сессий | Не выводить их из TSS, часов доступности или M4 ceilings. Для будущего такого требования — явный Class A Domain/API handoff, не обязательный новый API для S4 v1 |
| Прогноз | forecast.points[].date/ctl/atl/tsb | Сценарий модели за даты точек; не назвать концом гонки без факта события. Есть начало/конец и доступные датированные значения; пустые/неполные точки — явный data gap |
| Вердикт прогноза | forecast.message/final_tsb | Не рендерить legacy message как вывод об эффективности/риске. Нейтрально назвать модельный прогноз и показать числа; не классифицировать TSB своими порогами. Не обещать пик/поддержание формы/достижение цели |
| Сохранение | confirmation.status/is_current/replayed, plan_id и lifecycle | Applied receipt ≠ обязательно текущий план; неизвестные старые поля остаются unknown; plan_id сам по себе не доказывает активность |

Ни один пункт не требует нового endpoint или доменного вычисления в браузере.
Новый server-owned comparison с обеими датированными областями/сопоставимостью,
агрегат физических минут/сессий, точное время исходных измерений или подробный
causal audit — отдельные запросы Domain/API, если владелец расширит S4 v1.
До них указанные fallback обязательны; отдельного обязательного design approval нет.

## Неизменные границы / ASR

S1 preview_id-only confirm, frozen artifact, stale/CAS/expiry, uncertain retry,
S2 lifecycle/история и M3/M4 guards не меняются. Ни provider I/O, ни запись в личную
SQLite, ни миграция/новая таблица, ни исторический backfill не нужны. Legacy receipt
остаётся читаемым; новые объяснения не восстанавливаются из сегодняшнего контекста.
ASR-REL-1/2, MOD-2/3, PERF-4; ADR-0001/0006/0008/0009 переиспользуются. Новый ADR N/A:
слои/ownership прежние. Трасса и риски — docs/architecture/asr_catalog.md.
Не входит: переоценка нагрузки/физиологии, #703/#707, Recovery#669, полный redesign.

## Доказательства и handoff

[Probe и факты](reports/2026-10-22-planning-confirmation-s4-m1/README.md) фиксируют
две поддержанные публичные v2-сборки, отсутствие старых дат и разницу горизонтов;
это characterization, не RED новой UI-функции и не доказательство непонимания атлетом.
Авторский M1 результат проверяется отдельно от будущей реализации/успеха UX.

После независимой проверки M1: UI / Design Specialist получает этот spec, typed
BuildPreviewResponse/BuildConfirmResponse/EntryLoadAssessment в web/lib/types.ts,
PlanBuilder.tsx/EntryLoad.tsx и существующие E2E harness/fixtures. M2 — прототип и
реализация в этих контрактах с RED→GREEN по наблюдаемому поведению. Domain/API
получает только конкретный новый пробел, если fallback отклонён или нужного смысла
нет; такая часть останавливается до отдельного согласованного контракта/Class A.
Merge и live writes требуют владельца; M1 не даёт разрешение на них или UI-реализацию.
