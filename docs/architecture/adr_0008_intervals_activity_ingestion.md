# ADR 0008: Приём активностей из нескольких источников (Intervals-primary)

- Status: Accepted
- Date: 2026-07-22
- Related: `docs/intervals_primary_handoff_execplan.md` (M0), `activities` таблица, `activity_provider_links` (новая), `services/activity_ingest.py` (новый), `services/sync.py`, `services/intervals_icu.py`, `services/demo_mode.py`, `config/settings.py`, `docs/activity_tss_methodology.md`, ADR-0002

## Context

Трек Intervals-primary (`docs/intervals_primary_handoff_execplan.md`) требует, чтобы провайдерская активность становилась нашей канонической записью, способной нести идентичность и нагрузку ДВУХ источников (Garmin, Intervals) одновременно, не ломая инварианты проекта. Сегодня: `activities.activity_id TEXT PRIMARY KEY` — единственный ключ без провенанса; `source_tss` — одна колонка (у источников нагрузка разная); синк Garmin-gated (`services/sync.py:238`), пишет напрямую через `save_activities`. В БД уже есть не-Garmin строки — demo-активности `demo_activity_*` (`services/demo_mode.py:144`) и локально добавленные. Нужен зафиксированный, детерминированный контракт `provider data → canonical activity → planning` ДО кода адаптера.

## Decision

1. **Каноническая активность + provider-link модель.** `canonical_activity_id` = существующий `activities.activity_id` (потребители не ломаются). Связи — в `activity_provider_links(canonical_activity_id, provider, provider_activity_id, external_provider, external_id, provider_tss REAL, provider_payload TEXT, match_status, imported_at, UNIQUE(provider, provider_activity_id))`. `provider_payload` — JSON-снимок нормализованных полей источника: делает связь самоописывающей, чтобы каноническая строка была ДЕТЕРМИНИРОВАННОЙ ПРОЕКЦИЕЙ набора связей (п.4), а не зависела от порядка/истории записей. Колонка добавлена в CREATE TABLE напрямую (таблица введена в этом же непринятом PR — миграция не нужна). Связь `canonical_activity_id → activities.activity_id` — **логическая** (без SQLite `FOREIGN KEY`, как и прочие связи в схеме — `PRAGMA foreign_keys` выключен); отсутствие orphan-links закрепляется ТЕСТОМ, не декларацией. DB-констрейнты в DDL: `CHECK (match_status IN ('matched','ambiguous','unmatched'))` и `CHECK ((external_id IS NULL AND external_provider IS NULL) OR (external_id IS NOT NULL AND external_provider IS NOT NULL))` — статус ограничен тремя значениями, `external_id` невозможен без namespace `external_provider`. Одна каноническая может нести Garmin-link И Intervals-link. `match_status` — место хранения fail-closed «пометки для ревью». Миграция аддитивна и идемпотентна.

2. **Fail-closed сопоставление.** Точная пара (`external_provider`, `external_id`) связывает две записи в одну каноническую (`match_status='matched'`). Отсутствие/неоднозначность → НЕ склеивать: раздельные канонические, `match_status ∈ {unmatched, ambiguous}`. `external_provider` — обязательный namespace (иначе `external_id="123"` ложно «глобально уникален»). **Namespace берётся из Intervals `source` по ТОЧНОМУ whitelist, НЕ по подстроке**: только токен из `{garmin, garmin_connect, garminconnect}` даёт namespace `garmin` (тогда `external_id` — Garmin-id); любой другой источник, look-alike (`NOT_GARMIN` содержит «garmin», но НЕ Garmin), или отсутствие `source` → координата не создаётся (standalone). **`ambiguous` order-independent**: если координату (garmin, X) заявляют ДВА+ активности одного провайдера — НИ ОДНА не склеивается (нет произвольного «первый пришёл — matched»): каждая уходит на свою `intervals_<id>` и помечается `ambiguous`; настоящая Garmin-активность X остаётся `unmatched`. **Смена external identity**: связь переносится, каждая задетая каноническая ПЕРЕПРОЕЦИРУется из своих связей (п.4) — ушедший источник не оставляет ни полей/TSS, ни orphan/двойного учёта; каноническая без связей удаляется. Тесты: `test_ambiguous_*`, `test_external_identity_change_*`.

3. **TSS — явное исключение, ТОЛЬКО для Intervals; local-first.** `provider_tss` хранится ПО КАЖДОЙ связи и НЕ участвует в локальном каскаде расчёта `tss`. Fallback различает источники и **не обходит local-first**: `_normalize_intervals` потребляет уже вычисленную ПАРУ `tss`+`tss_method`, если строка её несёт, и тогда она приоритетна; текущий list-адаптер потоков не получает и каскад не гоняет (потоковый пересчёт — осознанный non-goal, методология 2026-07-09), поэтому для его «голых» строк **Intervals `icu_training_load`** становится каноническим `tss` ТОЛЬКО когда локальной пары нет, и тогда ЯВНО маркируется `tss_method="intervals_icu_provider_fallback"`. **Garmin `trainingLoad`** — Firstbeat/EPOC-нагрузка, НЕ TSS, и НИКОГДА не становится каноническим `tss`: для Garmin остаётся локальный каскад/heuristic (при нехватке данных — существующее поведение, не provider-fallback). Локальное время источника пишется в `date` (локальная дата); `started_at_utc` заполняется ТОЛЬКО из настоящего UTC-поля (`start_date`), локальное wall-clock туда не попадает. Это сознательное исключение — `docs/activity_tss_methodology.md` обновляется, а не декларируется нетронутым.

4. **Первичный источник + каноническая как проекция связей (order-independent).** Настройка `PRIMARY_ACTIVITY_SOURCE` (`config/settings.py`, env): значения `garmin`|`intervals`; **дефолт `garmin`** (обратная совместимость); Intervals-quickstart ЯВНО задаёт `PRIMARY_ACTIVITY_SOURCE=intervals`; **неизвестное значение → fail-fast** (`config.settings._primary_activity_source` бросает `ValueError`, не угадывает). Каждая связь несёт `provider_payload` (снимок полей источника); каноническая строка (`activities`) при любом событии ПЕРЕПРОЕЦИРУется из набора связей: берётся payload первичного источника, если его связь есть; иначе — детерминированно первого по алфавиту провайдера. `activities.source_tss` — legacy-проекция того же выбранного payload. Так результат — чистая функция от НАБОРА связей, не от порядка/истории; слияние, демоушен ambiguous и смена identity — без потерь и без «залипших» полей ушедшего источника. Каноническая без связей удаляется; связь без canonical не остаётся (одна транзакция). Проекция — create-or-UPDATE (НЕ `INSERT OR REPLACE`): повтор идентичного ingest не трогает `activities.created_at` (регресс-гейт `test_repeat_identical_ingest_preserves_created_at`). Обязательный тест: `Garmin → Intervals` ≡ `Intervals → Garmin` (совпадают canonical row, `tss`, `source_tss`, обе link). Канонический `tss`+`tss_method` первичны; `source_tss` — только совместимость.

5. **Ingest = нормализация + атомарная запись; курсор — НЕ здесь.** Разделены: `normalize_provider_activity(provider_row, source) -> candidate` (чистое преобразование, без БД) и `ingest_provider_activity(db, candidate) -> result`, которая в ОДНОЙ SQLite-транзакции upsert'ит canonical activity + provider-link + пересчёт `source_tss`-проекции (п.4). Курсор в этой транзакции НЕ продвигается (см. п.8): продвижение курсора внутри транзакции отдельной активности при сбое на N-й активности после уже-продвинутого курсора первой оставило бы данные за курсором необработанными. И Intervals-адаптер, и внутренний persistence Garmin (`services/sync.py`) пишут через `ingest_provider_activity` — нет полу-записанных состояний между `activities` и link. Инвариант no-orphan (link без canonical) закрепляется тестом публичного ingest, хотя прямой SQL его допускает (п.1). Внешнее поведение `sync_garmin_data` (сообщения/результат/окно) байт-в-байт неизменно.

6. **Два настроенных источника.** Приоритет — `PRIMARY_ACTIVITY_SOURCE`; дедуп — по (`external_provider`,`external_id`); coexistence, не overwrite. Слияние канонических полей — детерминированно (п.4).

7. **Backfill — офлайн и детерминированно, с классификацией.** Миграция/backfill НЕ обращаются к Intervals (никакого поиска `external_id` по сети) — работают офлайн. Классификация существующих строк по форме `activity_id`: `demo_activity_*` → `provider='demo'` (без внешнего link); уверенно Garmin (числовой Garmin-id) → `provider='garmin'`; иначе → `provider='legacy_unknown'` (НЕ притворяться Garmin). `external_id` при backfill — null; `provider_payload` ← снимок текущих полей активности (связь самоописывающая, п.4). `provider_tss` ← текущий `source_tss`. **Garmin-активность опознаётся резолвером по `provider_activity_id` (Garmin-id ЕСТЬ координата), а не по self-referential `external_id`**. Backfill немедленно разрешает уже существующие Intervals claimants и перепроецирует все затронутые canonical rows в той же транзакции: одна claimant-копия объединяется в одну каноническую с двумя `matched`-связями; две и более остаются отдельными `ambiguous` (fail-closed); сбой проекции откатывает и link, и merge. Это важно для старых строк вне incremental sync window — repair не зависит от будущего provider fetch. Backfill нормализует INTEGER/TEXT legacy IDs перед проверкой покрытия и пропускает активность, уже ПОКРЫТУЮ любой provider-связью (её id = чей-то `canonical_activity_id`) — включая проекционные канонические вроде `intervals_<id>`, иначе они были бы ошибочно классифицированы `legacy_unknown` и получили бы ложную вторую связь. Operator CLI `scripts/backfill_activity_provider_links.py` по умолчанию делает read-only aggregate preview и требует `--apply` для записи. Обязательные тесты: повторный backfill стабилен по матрице `garmin/demo/legacy_unknown` (идемпотентность); backfill до/после Intervals ingest даёт одну каноническую при unique claimant; ambiguous не угадывается; injected projection failure полностью откатывается; dry-run не мутирует SQLite и не раскрывает IDs/payload.

8. **Курсоры — продвижение только после успешного batch/window.** per-provider и per-domain (активности отдельно от wellness); `source` — в состоянии/результате job (`api/sync_jobs.py`); bootstrap ≥90 дней. Курсор продвигается ТОЛЬКО после того, как ВЕСЬ batch/window успешно проингещен — через `ingest_provider_batch(db, candidates, advance_cursor=…)` либо orchestration-транзакцию, — и НИКОГДА не внутри транзакции отдельной активности (п.5). Сбой на второй активности batch'а оставляет курсор прежним; повтор идемпотентно переобрабатывает обе (UNIQUE(provider, provider_activity_id) + upsert → без дублей); курсор двигается лишь при полном успехе. Персистентность курсора (таблица/строка состояния) заводится в M1 при подключении реального синка; в M0 контракт «advance-after-batch» фиксируется через инъецируемый `advance_cursor` и failure-injection тест.

9. **Rollback ≠ удаление link-таблицы.** После M1 удаление таблицы = потеря провенанса. Правильный rollback: отключить новый read/write path (вернуть прямой persistence), аддитивные данные (link-таблица, колонки) СОХРАНИТЬ. Физическое удаление — отдельная осознанная миграция только после backup.

## Consequences

- ✅ Ingest атомарен per-activity (canonical + link + `source_tss`-проекция в одной транзакции) — нет частично-записанных активностей и нет orphan-link'ов при сбое.
- ✅ Курсор продвигается только после успешного batch/window (не в per-activity транзакции): сбой в середине batch'а не оставляет данные за курсором; повтор идемпотентен (без дублей).
- ✅ Результат order-independent: `Garmin→Intervals ≡ Intervals→Garmin` (обязательный тест), повторный синк разных источников не меняет canonical.
- ✅ Backfill офлайн/детерминирован, честно классифицирует `garmin/demo/legacy_unknown`, не выдаёт наследие за Garmin; повторный прогон стабилен (матрица-тест).
- ✅ «Пометка для ревью» имеет представление в данных (`match_status`); rollback не теряет провенанс (аддитивные данные сохраняются).
- ⚠️ Link-таблица и ingest-funnel затрагивают persistence-путь Garmin-синка; внешнее поведение защищено снапшот-тестом. Миграция/backfill аддитивны, приемлемы для single-athlete SQLite (ADR-0002).
- ⚠️ `activities.source_tss` — вторична (legacy-проекция первичного источника); потребители «нагрузки» переходят на канонический `tss` или per-link `provider_tss` по мере необходимости.

## ASR / risk traceability (ADD 3.0)

M0 задевает три ASR (`docs/architecture/asr_catalog.md`):

- **ASR-REL-3** (обрыв sync не портит частичные данные) — `ingest_provider_activity` атомарен per-activity (одна SQLite-транзакция: canonical + link + `source_tss`-проекция); курсор двигается лишь после успешного batch'а (`ingest_provider_batch`), а не в per-activity транзакции, поэтому сбой не оставляет ни полу-записи, ни данных за курсором. Проверка — schema/ingest/batch-failure тесты.
- **ASR-MOD-3** (смена схемы обратно-совместима) — миграция `activity_provider_links` аддитивна и идемпотентна; потребители `activity_id` не ломаются. Проверка — schema RED→GREEN тест.
- **ASR-PERF-3** (инкрементальный sync) — per-provider/per-domain курсоры не раздувают окно при activity-only синке.

## Обязательные RED-матрицы для M0

- Порядок источников: `Garmin → Intervals` == `Intervals → Garmin` (canonical row, `tss`, `source_tss`, обе link совпадают).
- Классификация backfill при повторе: `garmin` / `demo` / `legacy_unknown` стабильны и не мутируют.
- Backfill→merge регресс-гейт: existing Garmin-активность → backfill (external_id null) → Intervals-копия → ОДНА каноническая с ДВУМЯ matched-связями (Garmin опознаётся по `provider_activity_id`, а не external_id) — нет задвоения нагрузки.
- Идемпотентность backfill после ingest: backfill не плодит `legacy_unknown` для проекционной канонической `intervals_<id>` (пропуск уже-покрытых).
- Идемпотентность повторного ingest: повтор идентичного ingest НЕ меняет `activities.created_at` (create-or-UPDATE, не REPLACE).
- Batch-курсор при сбое (guardrail п.5/п.8): batch из двух активностей, вторая падает → курсор ПРЕЖНИЙ; повтор обрабатывает обе без дублей; курсор продвигается ТОЛЬКО после полного успеха.
- No-orphan на уровне ingest: публичный `ingest_provider_activity` НИКОГДА не оставляет link без canonical (canonical + link — одна транзакция), хотя прямой SQL orphan допускает (п.1).
- Атомарный rollback (постоянный тест): сбой записи canonical внутри транзакции откатывает и link → `0 activities / 0 links` (`test_write_provider_activity_rolls_back_atomically`).
- Fail-closed сопоставление (п.2): только точный Garmin-`source` даёт garmin-namespace (`NOT_GARMIN`/Strava/пусто → standalone); ДВА претендента на одну координату → ОБА `ambiguous` независимо от порядка (нет произвольного winner); смена external identity перепроецирует старую каноническую (нет залипших полей/TSS, нет orphan/двойного учёта); `clear_all_data` очищает provider-links.
