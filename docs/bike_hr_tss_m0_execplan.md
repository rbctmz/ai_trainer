# Bike HR TSS — M0 (issue #444)

- **Статус:** M0 завершён — решение вынесено, продукт TSS не менялся
- **Ветка:** `dsh/bike-hr-tss-m0`
- **Скрипт (воспроизводимый):** `research/issue444_m0_bike_hr_tss.py`
- **Прогон:** `python research/issue444_m0_bike_hr_tss.py --db ai_trainer.db` (read-only)

## Решение (вердикт M0)

**«Нужны дополнительные данные»** для персональной HR-модели (M2/M3): на текущей
истории 15 качественных пар power+HR, FTP менялся в середине периода, а
коэффициенты NNLS-модели нестабильны и немонотонны. Одновременно M0 выявил две
более дешёвые корректировки, не требующие новых данных:

1. **Provenance-gap в Power TSS.** Хранимый `tss` для вело-активностей с мощностью
   пересчитан с *текущим* FTP (172), а не с FTP на дату тренировки (159 до
   2026-07-29). Целевая Power-TSS в БД систематически занижена (~15%) для
   тренировок до смены FTP. Это искажает любую калибровку по «цели».
2. **Порядок fallback стоит пересмотреть.** Текущая формула по средней ЧСС
   (`hr_tss_bike`) уже точнее и практически несмещённая (bias +0.1) по сравнению
   с фиксированными весами HR-зон (`hr_zone_tss_bike`, bias −16.5), но каскад
   выбирает зоны раньше. Зоны систематически занижают тяжёлые тренировки
   (bias −28.9 TSS в верхнем терциле).

Эти два пункта — кандидаты в M1 (корректирующие), персональная модель — M2/M3
после накопления данных.

## Текущий каскад (код)

`data/data_processor.py::ActivityProcessor.resolve_tss`, ветка `bike`:

1. `power_tss_bike` — `hours × (NP/FTP)² × 100` (`_power_tss`);
2. `hr_zone_tss_bike` — `Σ minutes_z × weight_z`, `_BIKE_HR_ZONE_TSS_WEIGHTS =
   (0.2, 0.35, 0.65, 0.95, 1.3)` (`_zone_weighted_tss`);
3. `hr_tss_bike` — `hours × (avgHR/LTHR)² × 100` (`_hr_tss`);
4. `heuristic_duration_bike` — `60 TSS/час` (`_heuristic_tss`).

`data/database.py::_repair_legacy_activity_tss` пересчитывает **всю** историю по
текущему `resolve_athlete_tss_profile` (последний FTP), перезаписывая `tss`,
`tss_method`, `tss_ftp_used`. Это источник provenance-gap: тренировки июля
(когда FTP=159) получили FTP=172.

## Кандидаты (сравнение)

1. **HRSS (Karvonen/hrTSS)** — `hours × ((avgHR−RHR)/(LTHR−RHR))² × 100`
   (входы: avgHR, RHR, LTHR, moving duration). Это TrainingPeaks-стиль hrTSS;
   точная формула Intervals.icu не верифицирована (открытый вопрос).
2. **Фиксированные веса HR-зон** — текущий `hr_zone_tss_bike`.
3. **Формула по средней ЧСС** — текущий `hr_tss_bike`.
4. **Персональная модель** — NNLS `minutes_z → Power TSS` (неотрицательные
   коэффициенты), обучение только на прошлом (хронологически).

## Ответы на открытые вопросы M0

1. **Какая формула = HRSS / normalized TRIMP?** Для M1 предлагается Karvonen
   hrTSS (`hours × ((avgHR−RHR)/(LTHR−RHR))² × 100`) — уже на TSS-шкале и
   вычислима из агрегатов. Классический Banister TRIMP — не на TSS-шкале, требует
   калибровочного множителя → относится к семейству персональной модели, не к
   фиксированному базлайну. Точную формулу Intervals.icu сверить отдельно
   (форумные ссылки из issue).
2. **Производные агрегаты или секундный ряд?** Для M1-кандидата достаточно
   агрегатов (avgHR, RHR, LTHR, длительность). Полный ряд не нужен → **политика
   #390 (не хранить streams) сохраняется**, новый ADR не требуется. Если позже
   понадобятся кардиодрифт/время-в-зонах по индивидуальным зонам — отдельный ADR
   на производные признаки.
3. **Доля качественных пар power+HR?** 15/29 вело (52%), с зонами 13/29.
4. **Разделять indoor/outdoor и равномерные/интервальные?** Да. Indoor (тренажёр)
   и outdoor различаются связью ЧСС↔мощность (охлаждение, инерция); интервалы vs
   равномерные — тоже. На 15 точках разделить нельзя → обязательно для M2.
5. **Жара/болезнь/кардиодрифт/задержка ЧСС?** Не вычислимо из хранимых агрегатов;
   нужен stream (on-demand) + внешний контекст (погода). Вне M1; в M2 — исключать
   или явно помечать такие сессии через прокси кардиодрифта.
6. **Практически значимая граница улучшения?** Предлагается фиксировать до M2/M3:
   MAE ≤ ~75% от лучшего фиксированного базлайна (здесь базлайн MAE≈11.0 → порог
   ≈8.3) **и** |signed bias| ≤ 5 TSS на хронологическом holdout.
7. **Минимальное разнообразие?** easy/moderate/hard терцили по ≥8 пар каждый +
   длительности <30/30–60/>60 мин + indoor/outdoor. Текущие 15 пар этому не
   удовлетворяют.
8. **Только вперёд или backfill?** По умолчанию только вперёд; backfill — отдельное
   контролируемое действие.

## Правила качества (для M2)

Тренировка допускается в обучающую пару только если одновременно:
- есть мощность и ЧСС; нормализован как `bike`;
- покрытие обоих сигналов относительно moving duration достаточное (порог — по
  данным M1, ориентировочно ≥ 80%);
- NP, FTP (на дату) и LTHR валидны и сохранены;
- нет недопустимых разрывов/«залипаний»/физически невозможных значений;
- пара не является ручным/провайдерским TSS без локально проверяемой мощности;
- помечены (или исключены) жара/болезнь/выраженный кардиодрифт.

Активация персональной модели — только при выполнении гейтов из issue (#444,
раздел «Активация») и границ из п.6–7 выше.

## Трассировка ASR

| Требование | ASR | Тактика в плане |
|---|---|---|
| Отсутствие входов → data gap, не падение | **ASR-REL-2** | HR-каскад fail-closed по уровням; отсутствие RHR/HRmax/покрытия деградирует к следующему безопасному базлайну |
| Обрыв sync не портит частичные данные | **ASR-REL-3** | производные признаки пишутся атомарно в общем ingest, cursor-after-clean-batch |
| Смена схемы обратно-совместима | **ASR-MOD-3** | новые поля provenance/признаков — аддитивные, migrate-on-read |
| Инкрементальный sync, дельта < 10 сек | **ASR-PERF-3** | признаки считаются в существующем per-provider окне, без отдельного полного прохода |

## ExecPlan (контур)

### M1 — provenance-фикс + безопасный базлайн (без персональной модели)

- исправить Power-TSS provenance: `tss_ftp_used` и `tss` по FTP на дату (или
  хранить версию профиля), не перезаписывать историю молча; завести отдельный
  issue на корректировку `_repair_legacy_activity_tss`;
- реализовать Karvonen-HRSS с версией формулы, происхождением и причиной fallback;
- собирать качественные пары power+HR в теневом режиме (признаки при синке, без
  сырого ряда);
- диагностическое сравнение только в dev/admin-отчёте;
- проверить перестановку зон/avgHR как *кандидат*, не меняя продуктовый TSS до
  подтверждения на большем числе точек.

### M2 — персональная модель в тени

- простая ограниченная модель (неотрицательные, монотонные коэффициенты);
- append-only версии + метрики; хронологическая (walk-forward) проверка;
- сравнение с **лучшим** фиксированным базлайном; без влияния на канонический TSS.

### M3 — контролируемая активация + UI

- активация только при выполнении M0-гейтов; авто-отключение при дрейфе;
- источник + уверенность в API/web-контракт; отдельная стратегия backfill и
  проверка влияния на CTL/ATL/TSB.

## Вне scope (без изменений)

- замена Power TSS пульсовой моделью при наличии мощности;
- бег/плавание персональные модели;
- Garmin `trainingLoad` как канонический TSS;
- многопользовательская схема с `athlete_id`;
- автоматический backfill всей истории.
